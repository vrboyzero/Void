# 灵榜会话功能实现方案计划

## 1. 目标

让 Codex、其他 AI 或 Agent 可以通过标准协议，向已经运行的 DeepSeek Harness Web 进程下达会话级任务，并能够：

1. 打开或登记一个已有项目目录，作为新的 Harness Workspace。
2. 在新 Workspace 中创建新 Session。
3. 在已有 Workspace 中创建新 Session。
4. 向已有 Session（包括可恢复的冷 Session）发送普通对话、转向指令或上下文注入。
5. 查询任务状态、会话状态和有限的会话事件。
6. 让用户配置一组反向通知和调用约束，使外部 Agent 知道必须提交什么文档、遵守什么规则以及如何等待结果。

本方案只规划“控制已经运行的 Web profile”这条主路径，不把外部 Agent 的任务误建成一个独立的 DSH 进程。

### 核心结论

- 采用 **DeepSeek Harness 插件 + 插件内嵌 MCP Server** 的实现方式。
- MCP Server 放在 DeepSeek Harness 插件内部，与 Web profile 运行在同一个 DSH Node 进程中。
- 插件通过 DSH 的 `WebServer.register()` 暴露 MCP Streamable HTTP 端点，供 Codex、其他 AI 或 Agent 连接。
- 插件负责访问和编排当前 Web profile 的 Workspace、Session、Agent 及事件；MCP 只作为外部 Agent 调用这些能力的标准协议。
- 不单独部署一个位于 DSH 进程外的控制型 MCP Server，避免无法直接访问当前 Web Session，以及产生独立状态源和会话一致性问题。

因此，本方案中“插件”和“MCP”不是二选一：**插件是实现与权限边界，MCP 是外部调用协议；MCP Server 的实际承载位置是 DeepSeek Harness 插件内部。**

## 2. 已确认的代码事实

分析对象：

- `参考项目/deepseek-harness-dsh-v0.1.6-alpha.1`
- `C:/Users/admin/.dsh`
- 当前 Void workspace 的 `packages/*`

关键事实：

### 2.1 DSH 的扩展边界是 Cordis Plugin

参考项目根部 `AGENTS.md` 和 `docs/architecture.md` 明确要求新行为通过插件扩展，不能直接改 `agent-loop`。能力应拆成 Service Definition、Service Provider 和 Consumer。会话中可见的内容必须能从 Session event log 重建。

因此控制能力应是一个 DeepSeek Harness 插件，而不是在 Web 进程外另写一个“旁路控制器”去读取 Session 文件。

### 2.2 WorkspaceController 能登记目录，但不创建项目目录

`packages/api/workspace-controller/src/index.ts` 和 `src/commands.ts` 提供 `WorkspaceController.create({ path })`。该命令会调用 `workspaceRegistry.resolveByPath()` 或 `workspaceRegistry.create()`，后者登记一个已有目录；它不会创建磁盘目录。

因此首版的“打开新项目”定义为：接收一个已有的绝对目录，校验后登记为 Workspace。若以后要创建目录，应另设显式、受权限控制的操作，不能把目录创建隐含在 `openWorkspace` 中。

### 2.3 SessionController 已有目标能力

`packages/api/session-controller/src/index.ts` 和 `src/commands.ts` 已提供：

- `create({ workspaceId | cwd, sessionId?, agentPreset? })`
- `list()`、`inspect()`、`page()`、`follow()`
- `prompt({ sessionId, requestId, mode: 'queue' | 'steer', content })`
- `fork()`、`cancel()`、`updateQueue()`

`session.create` 可以绑定 Workspace；`session.prompt` 会解析或恢复目标 Agent，并把 `requestId` 写入用户消息来源，重复请求可以通过该标识实现幂等。

### 2.4 Agent Runtime 已有三种消息投递语义

`packages/core/agent/src/runtime-types.ts` 的公开接口包括：

- `followup(message)`：排队一个普通后续回合并唤醒 Agent。
- `steer(message)`：向当前步骤转向；空闲 Agent 也会启动回合。
- `inject(message)`：注入下一步模型上下文，不主动唤醒 Agent。
- `whenIdle()`：等待 Agent 达到整体空闲。

控制插件应通过现有 SessionController/Agent API 编排，不应直接触碰循环内部状态。

### 2.5 现有 MCP 包是 Client，不是 DSH 控制 Server

`packages/mcp/mcp-client/README.md` 和 `src/index.ts` 说明，`@deepseek-ai/dsh-mcp-client` 的职责是让 DSH Agent 调用外部 MCP Server，并将外部工具注册到 `ctx.tools`。它不能直接控制已经打开的 Web Session。

### 2.6 ACP 可作为参考，但不是本需求的主路径

`packages/acp/acp` 已实现 ACP stdio Server，支持 `session/new`、`session/list`、`session/resume`、`session/prompt`、`session/cancel` 和语义更新。

但 ACP 运行在独立的 `acp` profile，天然拥有自己的连接和会话集合；它不是已经打开的 `web` profile 的控制面，也没有本需求的 Workspace Registry 语义、任务账本和用户定义的反向通知。ACP 适合后续做兼容适配或独立自动化，不替代本方案。

### 2.7 WebServer 可由插件注册路由，但默认不提供通用认证

`packages/host/webserver/src/index.ts` 的 `WebServer.register()` 只负责路由分发。README 明确说明 WebServer 本身没有 TLS、认证和 Origin 策略。

`packages/client/connection` 的 `ctx.connection` 可以提供浏览器 Cookie/Origin 认证的 `/api` 通道，但该认证模型面向浏览器，不适合 Codex 这类外部 Agent 直接复用。因此 MCP 控制端点必须由控制插件自己做 Bearer token 认证，或者后续增加专门的机器调用凭据能力。

### 2.8 当前本地版本存在版本差异

参考源码目录名是 `0.1.6-alpha.1`，当前 Void workspace 的 `node_modules/@deepseek-ai/dsh` 是 `0.1.0-rc.6`。`.dsh` 目录主要保存用户设置、Profile 和运行数据，不能把参考源码的 API 签名直接当成当前安装包的稳定契约。

实现前必须对实际安装的 DSH package 做一次类型和导出探测，并锁定兼容范围。首版不应同时支持多个未经验证的 Session API 版本。

## 3. 结论：推荐“DSH Plugin + MCP Server”混合方案

推荐架构：

```text
Codex / 其他 Agent
        │ MCP Streamable HTTP
        │ Authorization: Bearer <machine token>
        ▼
DeepSeek Harness Web profile
  └─ @void/void-dsh-control（Cordis Plugin）
       ├─ Control Service / Orchestrator
       │    ├─ WorkspaceController
       │    ├─ SessionController
       │    └─ Agent / Session events
       ├─ Control-plane Ledger（独立于 Session log）
       ├─ MCP Server Consumer
       └─ Settings / Policy Provider
```

这里的“插件”和“MCP”不是二选一：

- **插件**是实现边界。只有插件在 DSH 进程内，才能直接访问当前 Web profile 的 Workspace、Session、Agent、事件和存储服务。
- **MCP**是外部通信协议。Codex、其他 Agent 和未来的自动化程序可以用标准 MCP Client 连接，不需要了解 Cordis、Typert 或 DSH 内部 API。

如果只能选一个，必须优先做 DSH Plugin；但单独的插件没有标准的跨 Agent 调用面，因此交付形态应是插件内嵌 MCP Server。

## 4. 方案比较

| 方案 | 能否控制已打开的 Web Session | 外部兼容性 | 实现风险 | 结论 |
|---|---:|---:|---:|---|
| 仅外部 MCP Server | 弱，需要另一个私有 HTTP/文件接口 | 高 | 会话状态脱离 DSH 进程，容易出现两个事实源 | 不推荐 |
| 仅 DSH Plugin + 私有 HTTP | 强 | 低 | 自定义客户端和流式语义，后续维护成本高 | 可作为内部调试，不作为公开协议 |
| 独立 ACP profile | 只能管理 ACP 进程自己的 Session | 中高 | 无现有 Web Workspace、任务策略和回调语义 | 可做后续适配 |
| **DSH Plugin + MCP Server** | **强** | **高** | 需要实现认证、账本和 MCP 传输 | **推荐** |

## 5. 插件交付形态

建议在本仓库新增一个独立 DSH 插件包：

```text
packages/void-dsh-control/
  package.json
  cordis.patch.yml
  src/
    index.ts              # Cordis function plugin 入口
    service.ts            # DshControl Service Definition
    orchestrator.ts       # Workspace/Session 编排
    protocol.ts           # MCP 输入输出和错误类型
    policy.ts             # 用户配置的调用约束
    ledger.ts             # control-plane 持久化
    events.ts             # 任务状态和 Session 事件聚合
    mcp.ts                # MCP Server 和 HTTP Adapter
    auth.ts               # Bearer token、权限和请求限制
  tests/
    protocol.spec.ts
    auth.spec.ts
    ledger.spec.ts
    orchestrator.spec.ts
    real-composition.spec.ts
    mcp-http.spec.ts
```

包采用 DSH 的 function plugin 形式，使用 named exports：`name`、`inject`、`Config`、`apply`，不要混用 default export。依赖以 DSH peer dependencies 声明，版本以实际目标 profile 的 DSH 版本锁定。

建议插件名：`@void/void-dsh-control`，运行时名称：`void-dsh-control`。

`cordis.patch.yml` 只负责把插件插入 Profile，不改变 DSH 核心 Bundle。该包可以作为 Void 的独立 bundle，也可以追加到现有 `@void/void` 组合包；首版应保持独立开关，便于回滚。

## 6. MCP 工具和协议

### 6.1 工具清单（MVP）

#### `dsh_control_info`

返回：

- 协议版本和插件版本。
- 当前可用能力。
- 支持的 Workspace/Session target 类型。
- 用户配置的 `callerInstructions`。
- 必填字段和文档提交规则。
- 最大消息、文档引用、等待时长和并发限制。
- 当前调用方拥有的权限范围。

外部 Agent 在首次调用前应读取该工具。`callerInstructions` 不应只放在 MCP Server 的静态 instructions 中，因为用户设置可能通过 HMR 或设置页更新；工具响应必须是权威来源。

#### `dsh_dispatch_session_task`

高层原子操作，一次完成 Workspace 解析、Session 创建/恢复和消息投递，避免调用方自己拼装多个易错步骤。

建议输入：

```json
{
  "requestId": "caller-generated-id",
  "target": {
    "workspace": { "path": "E:/work/project" },
    "session": "new"
  },
  "messages": [
    {
      "text": "请完成任务，并先阅读任务文档。",
      "mode": "queue",
      "documentRefs": [
        { "path": "docs/task.md", "mode": "reference" }
      ]
    }
  ],
  "wait": { "until": "accepted", "timeoutMs": 10000 },
  "metadata": {
    "objective": "完成任务",
    "acceptanceCriteria": ["测试通过"]
  }
}
```

约束：

- `requestId` 必填，并按 `callerId + requestId` 做幂等。
- `messages` 中每个消息最终通过 DSH 的 Session prompt/inject/steer 入口进入会话日志。
- 外部调用方不能覆盖用户配置的调用规则。
- `metadata` 用于控制面审计和校验，不自动替代发给 DSH Agent 的对话内容；需要模型看到的内容必须明确进入 Session message。
- `wait` 只控制 MCP 响应等待方式，不改变 Agent 的运行策略。

返回至少包含：

```json
{
  "taskId": "task-...",
  "sessionId": "session-...",
  "workspaceId": "workspace-...",
  "status": "accepted",
  "eventCursor": "17",
  "callerInstructions": "...",
  "instructionsVersion": 3
}
```

#### `dsh_list_workspaces`

列出已登记 Workspace，可按路径前缀过滤。默认只返回 `workspaceId`、规范化路径、标题和 Session 数量，不返回密钥或环境变量。

#### `dsh_list_sessions`

按 Workspace 或绝对路径过滤 Session，返回 `sessionId`、`cwd`、运行状态、标题、更新时间和是否可恢复。使用现有 SessionController/SessionPersistence 的只读查询。

#### `dsh_send_message`

向已有 Session 发送一个普通对话消息。默认 `mode: queue`；只有具备 `session.steer` 权限的调用方才能使用 `mode: steer`。

#### `dsh_inject_context`

向下一步模型上下文注入信息，不唤醒空闲 Agent。该操作必须在响应中明确标记为“已注入但未执行”，避免调用方误以为任务已经运行。

#### `dsh_get_task`

查询控制任务的状态、目标 Session、最近事件、最后一个事件游标、错误摘要和有限的助手输出摘要。

#### `dsh_wait_task`

按 `taskId` 和 `afterCursor` 长轮询或等待到指定状态。返回有序事件和新的游标；调用方断线后可从游标继续，不依赖 MCP Server 主动推送自定义通知。

#### `dsh_cancel_task`

取消控制任务对应的活动回合。取消只调用 DSH 现有 cancel 语义，不删除 Session、不删除 Workspace、不清理项目文件。

### 6.2 可选工具

以下能力不放入第一版核心闭环：

- `dsh_read_session_events`：有界分页读取已持久化事件。
- `dsh_fork_session`：从已完成回合 fork 新 Session。
- `dsh_create_project_directory`：创建新目录，必须单独授权并有明确回滚语义。
- `dsh_open_existing_session`：如果 `dispatch` 的 target 语义已覆盖，不再重复暴露。

## 7. Workspace 和 Session 语义

### 7.1 Workspace target

支持两种寻址：

```text
{ workspaceId }
{ path: absolutePath }
```

路径模式执行以下步骤：

1. 规范化绝对路径并执行 `realpath`。
2. 确认路径存在且为目录。
3. 检查 `allowedRoots`；允许根为空时不允许通过路径打开，除非用户明确配置了根目录。
4. 调用 `workspaceController.create({ path })` 登记或解析已有 Workspace。
5. 返回规范化的 Workspace projection。

首版不创建磁盘目录。`workspaceRegistry.create()` 的现有语义只是登记已有目录；这也是避免外部 Agent 意外创建项目或写入任意盘符的安全边界。

### 7.2 Session target

支持：

```text
"new"
{ "sessionId": "existing-id" }
{ "forkFrom": "existing-id", "atSeq": 123 }
```

行为：

- **新 Workspace + 新 Session**：先登记 Workspace，再 `sessionController.create({ workspaceId })`。
- **已有 Workspace + 新 Session**：直接使用 Workspace ID 创建并自动绑定。
- **已有 Workspace + 已有 Session**：检查 Session 的 `cwd` 与 Workspace 路径一致，再发送消息。
- **冷 Session**：由 SessionController 的现有恢复策略恢复，不由插件直接打开 Session 文件。
- **运行中 Session**：普通消息默认排队；转向消息明确使用 `steer`；禁止不同外部任务无标识地竞争同一 Session。
- **fork**：只允许从可 fork 的已完成回合创建，沿用 DSH 的 fork 校验，不复制未完成队列。

### 7.3 并发和所有权

控制插件维护 `sessionId -> activeTask` 的进程内互斥表，并在账本中记录持有者。默认策略：

- 同一 Session 同时只有一个外部控制任务拥有“当前任务锁”。
- 普通消息可以在没有任务锁时排队，但每条消息必须有独立 `requestId`。
- `steer`、`cancel` 只能作用于任务拥有的 Session，或由显式的高权限 token 调用。
- 插件卸载时停止接受新任务，等待已接纳操作落入 `failed`/`cancelled`，再释放锁。

## 8. 对话和任务文档输入

用户需求中的主要输入是“会话中的对话”。因此首版把对话作为一等输入，而不是要求调用方先写控制文件。

### 8.1 消息

每条消息至少包含 `text`，可选 `mode` 和 `documentRefs`。消息通过已有 Session prompt 入口写入 Session event log；不能只保存在控制插件内存中。

### 8.2 文档引用

文档引用建议支持两种模式：

- `reference`：只把经过校验的工作区相对路径告诉 DSH Agent，让 Agent 使用自身文件工具读取。
- `inline`：插件读取有界文本，作为同一条用户消息的明确上下文发送；读取内容、来源路径和截断标记必须一起进入会话日志。

限制：

- 默认只允许 Workspace 内的相对路径。
- 绝对路径只有在 `allowedRoots` 明确覆盖时才允许。
- 限制引用数量、单文件字节数和总字节数。
- 拒绝 `..` 穿越、符号链接逃逸、设备文件和目录引用。
- 不把 token、密码、`.credentials.yaml` 等敏感文件内容自动 inline。

### 8.3 发送给 DSH Agent 的内容

外部 Agent 应通过自然语言告诉 DSH Agent：目标、工作区、任务文档位置、验收标准和限制。例如：

```text
请在当前工作区完成以下任务。
任务文档：docs/task.md，请先阅读。
目标：...
验收标准：...
完成后请运行：...
```

插件可以提供结构化字段帮助校验，但不能把所有结构化字段偷偷拼成未记录的模型上下文。

## 9. 反向通知和调用约束

“反向通知”拆为两个明确层次，避免把规则和运行状态混为一谈。

### 9.1 用户配置的调用约束

用户在 DSH 设置中配置，例如：

```yaml
dsh-agent-control:
  callerInstructions: |
    下单前必须说明目标、验收标准和任务文档路径。
    文档引用使用工作区相对路径；不要发送密钥或完整环境变量。
  requiredFields:
    - objective
    - acceptanceCriteria
  requiredDocumentRules:
    - id: task-spec
      description: 必须提供任务规格文档
      required: true
      pathPattern: '^docs/.+\\.(md|txt)$'
  forbiddenPatterns:
    - 'BEGIN PRIVATE KEY'
  instructionsVersion: 3
```

这些规则由 DSH 用户控制：

- `dsh_control_info` 返回完整的当前规则。
- `dsh_dispatch_session_task` 的响应再次返回规则版本和关键约束。
- 请求校验失败时返回稳定错误码和缺失字段，不接受外部请求覆盖规则。
- 用户配置不应只依赖 MCP tool description；tool description 只能做提示，响应才是动态权威值。

建议的错误码：

```text
dsh-control/policy-required-field
dsh-control/policy-document-missing
dsh-control/policy-document-invalid
dsh-control/policy-forbidden-content
```

### 9.2 异步任务通知

控制插件向调用方公开以下状态事件：

```text
accepted
workspace_resolved
session_created
session_resumed
prompt_queued
running
assistant_message
idle
completed
failed
cancelled
```

首版不依赖 MCP Client 是否支持服务器主动自定义通知，而采用：

- 工具响应返回 `taskId`、`sessionId`、`eventCursor`。
- `dsh_get_task` 查询当前状态。
- `dsh_wait_task` 按游标等待事件。
- 可选 MCP Resource：`dsh://tasks/{taskId}/events`，用于支持 Resource 读取的客户端。

可选的用户配置 Webhook 用于不能持续保持 MCP 连接的调用方：

```yaml
callback:
  enabled: false
  url: ''
  secretEnv: VOID_DSH_CONTROL_CALLBACK_SECRET
  events: [completed, failed, cancelled]
  timeoutMs: 10000
  maxAttempts: 5
```

Webhook 要求：HMAC 签名、事件 ID、幂等键、超时、指数退避和去重。默认不发送完整会话记录，只发送任务摘要和游标；用户必须显式选择敏感字段。

## 10. Control-plane Ledger

会话日志和外部控制任务是两个不同事实源：

### 10.1 Session event log

保存 DSH Agent 实际看到的对话、工具调用、模型输出和失败。继续由 DSH `SessionPersistence`/Session log 负责。控制插件不直接写 JSONL，不重复保存模型可见内容。

### 10.2 Control ledger

保存外部调用的生命周期和投递事实，建议使用现有 `storageDomain`，而不是直接操作后端文件：

- `tasks`：`taskId`、`callerId`、`requestId`、状态、Workspace/Session、时间、最后游标、错误摘要。
- `task_events`：任务状态事件、事件序号、摘要、关联 Session seq。
- `idempotency`：调用方请求键到任务结果的映射。
- `callback_deliveries`：回调事件 ID、尝试次数、最后错误和投递状态。
- `policy_meta`：已发布规则版本和摘要，可选；规则正文仍以用户设置为准。

建议 `storageDomain` domain 名称为 `dsh_agent_control`，独立于 Workspace 和 Session projection domain，并使用 schema version。由于当前 storage-domain 没有跨表事务，状态写入应采用：

1. 先追加不可变的 task event。
2. 再更新 task projection。
3. 启动或恢复时用 event 记录修复 projection。

所有写操作必须可重放、幂等，并在异常时保留可诊断的状态，而不是返回“已完成”但没有账本记录。

### 10.3 生命周期恢复

进程重启后：

- `accepted`、`workspace_resolved`、`session_created`、`prompt_queued` 但没有终态的任务标记为 `failed` 或 `unknown`，不能假报成功。
- 有 `sessionId` 和 `requestId` 的任务先查询 Session 日志/队列，确认消息是否已经接收，再决定重试。
- `requestId` 幂等检查必须先于任何新的 prompt 投递。
- 已发送但回调未送达的任务保留在 `callback_deliveries`，按重试策略继续。

## 11. 插件配置和安全

建议配置：

```yaml
- id: void-dsh-control
  name: '@void/void-dsh-control'
  config:
    enabled: true
    transport: streamable-http
    path: /mcp/dsh-agent-control
    tokenEnv: VOID_DSH_CONTROL_TOKEN
    allowedRoots: []
    allowedOperations:
      - workspace.read
      - workspace.open
      - session.list
      - session.create
      - session.prompt
      - session.observe
    callerInstructions: ''
    requiredFields: []
    requiredDocumentRules: []
    notifyEvents: [accepted, completed, failed]
    callback:
      enabled: false
```

> **实现轮修正**（见 §26.2 与 §27）：
> - `tokenEnv` 是**单个**环境变量名，实现里改成了 `tokens: [{callerId, tokenEnv, operations}]`
>   列表，以便按调用方分别授权；环境变量名统一为 `VOID_DSH_CONTROL_TOKEN`。
> - `notifyEvents` **已从实现中删除**：它与 `callback.events` 语义重叠，且此前只被声明、
>   不生效。要控制通知范围请用 `callback.events`。上面这段保留为设计原文，**不要照抄**。
> - 用户可直接复制的配置样例见 §25.10。

安全要求：

1. 默认只绑定现有 WebServer 的 loopback 部署；不默认打开 `0.0.0.0`。
2. token 只从环境变量读取，不写入 `settings.yaml`、`cordis.patch.yml`、Session log 或普通日志。
3. Bearer token 比较使用常量时间比较；失败只返回通用 401，不泄漏 token 配置状态。
4. 根据 token 或配置授予最小操作权限；只读、下单、转向、取消分开控制。
5. `realpath` 后检查 `allowedRoots`，防止路径穿越和符号链接逃逸。
6. 限制 HTTP/MCP body、单条 prompt、文档引用、事件页和 callback payload 大小。
7. 所有请求带 `requestId`；服务端做幂等，重复请求不重复发送 Session 消息。
8. 不开放 shell、任意命令、任意进程、动态插件安装、任意 Session 文件路径和 token 读取。
9. 外部消息进入 DSH Agent 前必须通过已有 Session prompt/inject/steer 入口，以便写入事件日志。
10. 外部请求不能提升 DSH Session 的 sandbox、approval、模型权限或工作区范围。
11. callback URL 必须是用户配置，必要时做 URL allowlist；禁止由外部请求动态指定回调地址。
12. 返回给外部 Agent 的错误要稳定、可诊断且不包含凭据、环境变量和内部堆栈。

## 12. MCP HTTP 实现建议

参考项目的 `packages/mcp/mcp-client` 测试已经使用官方 SDK 的 `@modelcontextprotocol/server`、`createMcpHandler` 和 `@modelcontextprotocol/node` 的 `toNodeHandler` 做 Streamable HTTP 测试。控制插件应复用同一套 SDK 族，并按目标 DSH 版本固定依赖版本；不要自行实现 MCP JSON-RPC 和流式协议。

插件启动时：

1. 注入 `webServer`、`sessionController`、`workspaceController`、`agents`、`storageDomain` 等服务。
2. 建立控制 Service、ledger 和事件聚合器。
3. 创建 MCP Server，注册工具和可选 Resource。
4. 通过 `webServer.register({ kind: 'exact', path, handler })` 注册端点。
5. handler 先校验 HTTP Bearer token，再把请求交给 SDK Node adapter。
6. 插件卸载时先停止新请求，再等待任务编排器和回调投递 quiesce，最后注销路由和关闭 MCP handler。

不要把端点直接放进 `@deepseek-ai/dsh-mcp-client`；那个包的公共职责是 MCP Client。也不要把 MCP 端点挂在浏览器 `/api` RPC 上伪装成 Remote 方法，MCP 的 Streamable HTTP 生命周期与 Typert RPC 不同。

## 13. 事件聚合和输出边界

控制插件监听已有事件：

- `session/event`：读取已提交的 Session 事件，更新游标并提取有界的助手消息摘要。
- `agent/status`：映射 `running`/`idle`。
- `agent/error`：映射 `failed`，保留用户可读错误链。
- `session/created`、`session/disposed`：维护会话存在性和任务锁。

事件投影规则：

- 默认只返回事件类型、时间、状态、摘要和 Session seq。
- 助手文本设置最大字符数，超出时返回截断标记和继续读取游标。
- 工具参数、工具结果、文件内容和模型内部推理默认不通过控制面回传。
- 如果未来允许读取完整 Transcript，必须单独权限、分页和审计，不能隐含在 `dsh_get_task`。

## 14. 行为验收（BDD）

### 场景 A：打开已有项目并创建新会话

**Given** 调用方有 `workspace.open`、`session.create`、`session.prompt` 权限，且绝对路径存在于 `allowedRoots`。

**When** 调用 `dsh_dispatch_session_task`，target 为 `{ workspace: { path }, session: 'new' }`。

**Then** DSH 登记或复用该 Workspace，创建绑定该 Workspace 的 Session，消息进入 Session 日志，并返回 `taskId`、`workspaceId`、`sessionId` 和游标。

### 场景 B：已有 Workspace 创建新会话

**Given** Workspace 已登记。

**When** target 使用 `workspaceId` 和 `session: 'new'`。

**Then** 创建的新 Session 自动附着到该 Workspace，不重复创建 Workspace，不影响该 Workspace 的其他 Session。

### 场景 C：继续已有或冷 Session

**Given** Session 属于目标 Workspace，或者是可恢复的冷 Session。

**When** 调用 `dsh_send_message`，使用新的 `requestId`。

**Then** 消息被排队或转向；如果是冷 Session，DSH 按现有策略恢复；如果 Workspace 不匹配，调用失败且不写入新消息。

### 场景 D：重复请求幂等

**Given** 第一次请求已返回 `taskId` 或已接受消息。

**When** 使用相同 `callerId + requestId` 重试。

**Then** 返回原任务/原接受结果，不创建第二个 Session，不追加第二条相同用户消息。

### 场景 E：用户约束反向通知

**Given** 用户配置了必填 `objective`、`acceptanceCriteria` 和任务文档规则。

**When** 调用方先调用 `dsh_control_info`，再提交缺少任务文档的下单请求。

**Then** info 响应明确返回当前规则；下单被稳定错误拒绝，并指出缺少的字段/文档；调用方不能覆盖该规则。

### 场景 F：断线后按游标恢复

**Given** 任务已经产生事件并返回 `eventCursor`。

**When** 调用方断线后调用 `dsh_wait_task(taskId, afterCursor)`。

**Then** 只返回游标之后的有序事件，重复读取不会重复执行任务，最终可以观察到 `completed`、`failed` 或 `cancelled`。

### 场景 G：安全拒绝

**Given** token 缺失、权限不足、路径不在允许根目录或文档路径穿越。

**When** 调用对应工具。

**Then** 请求在投递到 Session/Agent 之前被拒绝，不执行命令、不创建文件、不写入模型可见消息，并返回不泄漏敏感信息的稳定错误。

#### ⚠️ 接客户端之前：暗号必须同时存在于两个地方

这一步**最容易漏**，漏了的症状是**静默 401**——客户端配置语法正确、能保存、也不报错，只是每个
请求都被拒。2026-09-20 真机接 Codex 时就栽在这里。

原因是**两个进程各读各的**，灵榜的鉴权是两边对称的（一边出示、一边校验）：

| # | 位置 | 谁读 | 作用 | 漏了会怎样 |
|---|---|---|---|---|
| ① | `~/.dsh/.env` | **DSH** | 校验来客 | 所有请求 401 |
| ② | **操作系统环境变量** | **客户端** | 出示身份 | 客户端不发凭据 → 401 |
| ③ | 客户端配置里的变量**名** | 客户端 | 指向 ② | 同上 |

> **客户端不读 `.env`。** 那是 dsh 自己的约定，不是客户端的。Codex / Cursor / Claude Code 都只认
> **自己进程的环境变量**——所以 ② 必须是真正的系统环境变量，不能只写 `.env`。

② 的设法（Windows 用户级，一次设置对所有客户端通用）：

```powershell
setx VOID_DSH_CONTROL_TOKEN "<和 ① 里完全相同的那串>"
```

**改完必须重启客户端**——它们在**启动时**读环境变量，已经开着的窗口拿不到新值。

①②③ 的变量名必须一致；**① 与 ② 的值必须逐字符相同**，否则照样 401。

> 顺带一个反直觉的坑：`codex doctor` **只检查变量存在且非空，不验证值是否正确**。实测四态——
> 变量不存在 → 点名；空串 → 点名；**真实值 → 不点名；错误值 → 也不点名**。
> 所以「doctor 干净」不等于「能连上」。详见 §29.10 ⑦。

客户端配置**在「虚空（Void）」面板的「MCP接入配置」分组里生成并复制**（见 §29.8）。代价是
下面这件事必须记下来：各客户端的字段名与取值**并不统一**，一份「通用片段」不可能对所有
客户端成立。2026-09-20 逐家核对官方文档的结果：

| 客户端 | `type` 字段 | 暗号怎么给 |
|---|---|---|
| Codex CLI | 无此字段 | 有专门的 `bearer_token_env_var`，暗号不必进配置 |
| Cursor | **不写**（官方远程示例没有） | `Bearer ${env:NAME}`，带 `env:` 前缀 |
| Claude Code | **必需**，取 `http`（`streamable-http` 是别名） | `Bearer ${NAME}` |
| Claude Desktop | 字段名叫 `transport`，取 `http` | 用户配置文件**只接 stdio**，必须 `mcp-remote` 桥接 |
| VS Code | 必需，取 `http` | — |

> **上表「暗号怎么给」一列，五种写法给的全是变量名，没有一个是值。** 差别只在语法形态：
> Codex 是独立字段 `bearer_token_env_var = "VOID_DSH_CONTROL_TOKEN"`，Cursor 是带前缀的
> `${env:VOID_DSH_CONTROL_TOKEN}`，Claude Code 与其余是 `${VOID_DSH_CONTROL_TOKEN}`。
> 把**值**填进这些位置不会报错，只会静默 401——因为客户端会去找一个以那串值命名的环境变量。

因此当初写在方案里的 `"type": "streamable-http"` **是错的**：没有任何官方文档把它当通用
取值，而 Claude Code 缺 `type` 会直接跳过该 server。上面这份表取代了原先的概念配置。

Codex 与 Cursor 两种写法不需要任何桥接，是首选；Claude Desktop 需要第三方桥接包，最脆弱。

验证：实际 Web profile 启动、token 认证、Codex tools/list/tools/call、从新路径创建 Session 并观察完成事件。模型 API 测试使用现有 mock/recorded harness，避免把真实密钥写入方案或测试。

### 20.3 插件安装方式：必须用 tarball（实测结论）

dsh 的模块解析是「双锚点」的：profile 目录内的包沿 Node 父级向上查找，命中
`$DSH_HOME/profiles/node_modules` 里镜像的安装依赖闭包（`dsh-app-boot` 的
`healProfilesModuleFallback`）。

`dsh plugin add <目录>` 会装成 `link:`（符号链接）。Node 按**真实路径**解析该包的
bare import，父级查找从 `E:\...\Void\dist\lingbang` 往上走，永远到不了 profile 的
`node_modules`，于是 peer 解析失败：

```text
Error: dsh: plugin tree failed to load: failed to import loader entry void-dsh-control
  (@void/void-dsh-control): Cannot find package '@deepseek-ai/cordis'
  imported from E:\project\star-sanctuary\Void\dist\lingbang\lib\index.js
```

改用 tarball 后 pnpm 把包解到 profile 自己的 `node_modules`，父级查找命中安装闭包，
启动成功。因此：

- `dist/lingbang/` 仍然是包体（用户要求的目录形态），同时产出
  `dist/lingbang/void-void-dsh-control-0.1.0.tgz` 作为安装载体；
- README §1.2 明确写了「必须用 tarball」及原因；
- 重新打包后要**先 remove 再 add**，否则 pnpm 按包名 + 版本复用已解析结果，
  返回 "Already up to date" 并保留旧代码（实测踩到过）。

### 22.2 实现中修正的设计点（与方案正文的差异）

1. **`completed` 的触发条件**：方案只列出状态，未定义何时进入 `completed`。
   实现取「任务先被观察到 `running`，随后 Agent 回到 `idle`」作为完成条件，并记录
   `idle` 与 `completed` 两条事件。用 `sawRunning` 集合避免同一 Session 上一轮遗留的
   `idle` 通知误关掉刚排队的新任务。
2. **`dsh_inject_context` 的任务终态**：注入不唤醒 Agent，任务在
   `prompt_queued → idle → completed` 立即收敛（事件摘要写明 "context injected; nothing executed"），
   MCP 响应额外带 `injected: true, executed: false`。否则这类任务会长期占用调用方并发额度。
3. **`record()` 必须重读投影**：初版把调用方持有的 `TaskRecord` 快照合并回账本，
   导致后续 `putTask` 覆盖掉前一步写入的 `sessionId` / `lastCursor`（实测 `dispatch`
   报 "dispatch completed without a workspace and session"）。已改为按 `taskId` 重读后再写。
4. **未知宿主错误统一收敛**：`toStableError()` 把非 `ControlError` 的宿主异常归一为
   `dsh-control/host-unavailable`，既记录到任务，也作为抛出值。
5. **MCP 传输改为有会话（stateful）而非 stateless**：stateless 模式下每个 POST 都新建
   `McpServer`，无法把「调用方身份」稳定绑定到一次连接，也没有重连语义。改为
   `Map<sessionId, {server, transport, callerId}>`：`initialize` 建会话，后续请求按
   `mcp-session-id` 复用，并且**会话与创建它的 callerId 绑定**——泄漏 session id 但没有
   对应 token 依然无效。带 64 会话上限 + 5 分钟空闲回收。
6. **`dsh_control_info` 不要求任何操作**：它的职责就是在调用方「还没有任何授权」时
   告诉对方规则，因此只要求认证。其余 8 个工具按 `TOOL_OPERATIONS` 表逐一下发授权。
7. **配置校验前置到同步阶段**：`apply()` 在注册 async effect **之前**完成
   `allowedOperations` / `tokens[].operations` / `forbiddenPatterns` 的校验，
   于是配置错误会让插件启动直接失败（`dsh plugin add` / Loader 调用抛错），
   而不是留下一个半成品端点。已用 composition 测试锁定。

### 25.1 这个插件是干什么的

你已经开着一个 DeepSeek Harness 的网页版（Web profile）。平时是你在网页上打字，
它干活。

装上这个插件以后，**别的 AI 也能指挥它干活**——比如让 Codex 说一句
「去把 E 盘那个项目里的登录 bug 修了」，你正开着的这个 DSH 就会真的去修，
修完把结果回报给 Codex。

打个比方：

| 现实里的东西 | 对应到这里 |
|---|---|
| 你的 DSH 网页版 | 一间办公室，一直开着 |
| 这个插件 | 在办公室墙上开的一个**服务窗口** |
| Codex 之类的 AI | 来窗口办事的**客户** |
| 下面要设置的 token | 客户进门前要对的**暗号** |
| `allowedRoots` | 允许客户进哪几间**档案室** |
| `allowedOperations` | 允许客户办哪几类**业务** |
| `callerInstructions` | 贴在窗口上的**办事须知** |

它**不是**一个独立程序，也不是另开一个 DSH。它只是给你已经在用的那个 DSH
加了一个对外的窗口。所以：DSH 关着，窗口就不存在；DSH 一重启，窗口跟着回来。

### 25.2 装之前先知道三件事

1. **默认谁也进不来。** 装完如果不配暗号，任何请求都会被挡在门外（返回 401）。
   这是故意的——宁可装完连不上，也不能装完就敞着门。
2. **暗号只放在环境变量里。** 不写进任何配置文件，不写进日志，也不写进对话记录。
3. **随时能关。** 出任何问题，在配置里把总开关改成 `false` 重启，窗口就没了。
   你的对话记录、项目文件夹、记账数据一个都不会丢。

### 25.3 安装

#### 第二步：先装到一个「试验用」环境里（强烈建议）

>
> ```text

>        omit --from-default-profile to use it

>
> 这不是故障，是 dsh 在防止把已装好的插件冲掉。**日常启动请用第四步的命令**
> （不带 `--from-default-profile`）。
>
> 顺带一提：`--from-default-profile` 建完会**直接启动** profile，所以要用 `Ctrl+C` 停，
> 这也是它容易被误当成"启动命令"的原因。

```powershell
# 3. 把插件装进这个试验环境

```

> 📌 **第二步设的 `DSH_HOME` 会影响本节后续所有 `dsh` 命令的目标环境。**
> 完整说明见本节末尾的「设了 `DSH_HOME` 的窗口里，`dsh` 命令指向哪里」。

#### 第三步：设置暗号（一条命令）

暗号是外部 AI 进入你 DSH 的唯一凭据。**不要用 `123456`、`888888` 这类固定值**——
它一旦被猜中，对方就能操作你的工作区和会话。

**推荐做法**：生成一条强随机暗号，写进用户级 `.env`。这个位置的好处是
**不管你从哪个目录启动 dsh 都生效**，不用记着 `cd`：

```powershell
$t = -join ((48..57)+(65..90)+(97..122) | Get-Random -Count 48 | ForEach-Object { [char]$_ })
Add-Content "$env:USERPROFILE\.dsh\.env" "VOID_DSH_CONTROL_TOKEN=$t"
"你的暗号: $t"      # 记下来，等下配给 Codex 要用同一串
```

`$env:USERPROFILE\.dsh\.env` 就是 `$DSH_HOME\.env`（`DSH_HOME` 为空时 dsh 用的默认 home）。

**为什么不用 `export`**：`$env:VOID_DSH_CONTROL_TOKEN = "..."` 只在当前窗口有效，关掉就没了，
下次启动 dsh 又变成没有暗号、所有请求 401。

##### 两个 `.env` 位置的区别

dsh 启动时会读两个文件，把里面的变量填进进程环境（只在同名变量尚未设置时填）：

| 文件 | 作用范围 | 什么时候用 |
|---|---|---|
| `$DSH_HOME\.env`（= `C:\Users\<你>\.dsh\.env`） | 用这个 home 的**所有** dsh，与启动目录无关 | **推荐，普通用户选这个** |
| `<你运行 dsh 的目录>\.env` | 只影响从该目录启动的 dsh | 想给某个项目单独配一套时 |

仓库根也放了一份 `Void\.env` 模板（已被 `.gitignore` 忽略），从 `Void\` 目录启动时会读到它。
如果两处都有，**启动目录的那个优先**——所以两处最好填同一个值，否则会出现
"从不同目录启动，暗号不一样"的怪事。

##### 只设 `.env` 不够——客户端那一侧要单独设

上面这一步解决的是 **DSH 读暗号**。它**不会**让 Codex / Cursor 等客户端拿到暗号——
那些是**独立进程**，只认自己启动时继承的**操作系统环境变量**，不读 dsh 的 `.env`。

所以接客户端前还要再设一次（Windows 用户级，一次设置对所有客户端通用）：

```powershell
setx VOID_DSH_CONTROL_TOKEN "<和上面 .env 里完全相同的那串>"
```

两侧的分工与完整说明见 §阶段 6 的「接客户端之前」；真机踩坑记录见 §29.10 ⑦。

**要点**：① 与 ② 的值必须逐字符相同；**改完必须重启客户端**，它们在启动时读环境变量。

##### 在 WSL / Linux / macOS 里

**路径完全支持**：插件跑在 dsh 进程里，用的是平台原生的路径规则。WSL 下 dsh 是 Linux 进程，
`$DSH_HOME\.env` 就是 `~/.dsh/.env`（即 `/home/<你>/.dsh/.env`），与 Windows 侧互不干扰。

**但上面的命令是 PowerShell 方言**，WSL 里要换成：

```bash
t=$(od -An -tx1 -N32 /dev/urandom | tr -d ' \n')
mkdir -p ~/.dsh && printf '%s\n' "VOID_DSH_CONTROL_TOKEN=$t" >> ~/.dsh/.env
echo "你的暗号: $t"
```

`od` 和 `tr` 是 POSIX 标配，任何 Linux 发行版都有，不需要 openssl 或 python。
`mkdir -p` 是必要的——全新的 WSL home 里可能还没有 `~/.dsh` 目录。

> **插件会自己判断该给哪种命令。** 启动时的提示按 `process.platform` 选择方言：
> Windows 印 PowerShell，WSL / Linux / macOS 印 POSIX shell。你不用记这条规则，
> 照抄终端打印的那两行就行。
>
> **两个系统各有一套 dsh 时要注意**：Windows 侧读 `C:\Users\<你>\.dsh\.env`，
> WSL 侧读 `/home/<你>/.dsh/.env`，是**两个不同的文件**。哪边跑 dsh 就要在哪边配暗号。
> 想让两边共用一个，可以在 WSL 里把暗号文件软链到 Windows 侧，或两边填同一个值。

##### 没配暗号会怎样

插件**不会**敞开大门，而是拒绝一切请求（返回 401）。启动时终端会打印一段醒目提示，
里面直接带着上面那条修复命令，复制粘贴即可：

```text
[void-dsh-control] no usable machine token (VOID_DSH_CONTROL_TOKEN unset) and allowAnonymous is false:
[void-dsh-control] every request to the control endpoint will be rejected with 401
[void-dsh-control]   fix it once — dsh reads this file no matter which directory it is launched from:
[void-dsh-control]     $t = -join ((48..57)+(65..90)+(97..122) | Get-Random -Count 48 | ForEach-Object { [char]$_ })
[void-dsh-control]     Add-Content "C:\Users\<你>\.dsh\.env" "VOID_DSH_CONTROL_TOKEN=$t"
[void-dsh-control]   then restart dsh; full procedure: docs/灵榜会话功能实现方案计划.md §25.3
```

> 注意这些提示是**直接写到终端**的，不是写进网页日志面板——因为 dsh 的插件日志
> 默认只进 Web UI，坐在终端前的你看不到。

> ⚠️ **`DSH_HOME` 不能放进 `.env`。** `DSH_` 是 dsh 的 bootstrap 前缀（决定进程从哪加载
> 代码和配置），写进 `.env` 会让 dsh 直接启动失败并报
> `sets "DSH_HOME", which only the launching environment may set`。
> 它只能 `export`，或做成 Windows 用户级环境变量。
>
> 优先级：已存在的进程环境变量 **高于** `.env`。所以临时想换 token，直接 `export` 就能盖掉文件里的值。
>
> **token 的值不要写进 `settings.yaml`、`cordis.patch.yml`，也不要贴给别人。**
> `.env` 已被 git 忽略；确认一次：`git check-ignore -v .env`。

| 第五步 | `web` | 你**日常那个环境**的名字（dsh 出厂就叫这个） |

两条命令只差这一个词，别照抄上一步。

> 🛑 **执行前必须先确认 `DSH_HOME` 是空的。**
>
> 第二步设过 `$env:DSH_HOME`，如果它还在，这条命令**不会**装进你的正式环境，
> 而是在试验环境里**新建一个空白的 `web`** 然后把插件装进去。你会以为装好了，
> 正式环境一点没变。
>
> ```powershell
> "DSH_HOME = '$env:DSH_HOME'"     # 必须是空字符串
> ```
>
> 不是空的话，先清掉或**另开一个窗口**：
>
> ```powershell
> Remove-Item Env:\DSH_HOME
> ```

```powershell
# 1. 确认 DSH_HOME 为空（输出必须是 DSH_HOME = ''）
"DSH_HOME = '$env:DSH_HOME'"

# 2. 先停掉正在跑的正式 profile（原因见下面「为什么要先停再装」）
Stop-Process -Id <你正式 profile 的 PID>

# 3. 装进正式环境
dsh plugin --profile web add "E:\project\star-sanctuary\Void\dist\lingbang\void-void-dsh-control-0.1.0.tgz"

# 4. 确认真的装进去了（最可靠的一步，别跳过）
(Get-Content "$env:USERPROFILE\.dsh\profiles\web\package.json" -Raw | ConvertFrom-Json).dsh.profile.bundles
```

第 4 步应该看到 `@void/void-dsh-control` 出现在列表里：

```text
@deepseek-ai/dsh-base
@deepseek-ai/dsh-web-app
... 你原有的插件 ...
@void/void-dsh-control          ← 新增的
```

**没看到就说明装错地方了**，回到第 1 步重来。`dsh plugin add` 成功只代表 pnpm 装好了，
不代表装进了你想装的那个 home。

**同时留意安装输出**。正常情况**不会**出现 `initialized profile` 这行。
如果看到类似：

```text
dsh: initialized profile web at E:\...\.tmp\lingbang-smoke\profiles\web
```

路径里的 `.tmp\lingbang-smoke` 就是装错地方的证据。先按 §25.7 把它清掉，再回到第 1 步。

#### 为什么要先停再装

dsh 的热重载只监听 profile 的 `cordis.patch.yml`（`watchUserPatches` 只注册了这一个文件），
**不监听 `package.json`**，所以安装本身不会触发重载、运行中的进程也不会去加载新插件。

但 `pnpm` 会**重写 `node_modules`**。对一个正在运行的 Node 进程来说，这有理论风险
（它可能在之后懒加载某个被替换掉的包）。停掉再装、装完再起，成本很低，风险归零。

```powershell
# 找 PID（按 bin.js 精确匹配，避免把别的 node 进程也算进来）
Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
  Where-Object { $_.CommandLine -match 'dsh\\lib\\bin\.js' } |
  ForEach-Object {
    $p = if ($_.CommandLine -match '--profile\s+(\S+)') { $Matches[1] } else { '(默认 web)' }
    "PID $($_.ProcessId)  profile=$p"
  }
```

#### 必须用绝对路径

安装参数里的 tarball 路径**必须是绝对路径**。原因不是"dsh 按你的当前目录解析"——
真实机制更容易踩坑：

`dsh plugin` 里有个 `anchorPathSpec()`，但它**只处理以 `.` 开头的路径**：

```js
const match = /^(?:(?:file|link):)?(\.{1,2}(?:[/\\].*)?)$/.exec(argument);
if (match?.groups?.path === void 0) return argument;      // ← 不以 . 开头：原样透传
return `${prefix}${resolve(cwd, match.groups.path)}`;     // ← 以 . 开头：锚定到你的 cwd
```

而 pnpm 是以 **profile 目录**为 cwd 运行的（`spawnSync("pnpm", ..., { cwd: dir })`）。
所以透传过去的相对路径会被 pnpm 按 **profile 目录**解析，不是按你的当前目录。

实测（在仓库根执行，tarball 确实存在于 `Void\dist\lingbang\`）：

| 参数写法 | dsh 处理 | 结果 |
|---|---|---|
| `E:\...\void-void-dsh-control-0.1.0.tgz` | 透传（绝对路径） | ✅ 成功 |
| `.\dist\lingbang\void-...tgz` | 锚定到 cwd → 变绝对路径 | ✅ 成功 |
| `dist\lingbang\void-...tgz` | **透传** | ❌ pnpm 按 profile 目录找，不存在 |
| `file:dist\lingbang\void-...tgz` | **透传** | ❌ 同上 |

**结论：要么写绝对路径，要么写 `.\` 开头的路径。直接写 `dist\...` 在任何目录都会失败，
包括仓库根。** 统一用绝对路径最省心。

#### 装完之后：两个地址、两个 token，别搞混

**装完必须重启**（插件在启动时装载）。重启后你会看到两个完全不同的地址：

| | 网页界面 | MCP 控制端点 |
|---|---|---|
| 地址 | `http://127.0.0.1:3080/?token=a_oSArj...` | `http://127.0.0.1:3080/mcp/dsh-agent-control` |
| 谁用 | **你**，用浏览器打开 | **Codex 等外部 AI** |
| 那个 token | dsh 每次启动自己生成的浏览器信任令牌，打印在控制台 | 你在 `.env` 里配的 `VOID_DSH_CONTROL_TOKEN` |
| 从哪来 | 自动生成，不用你管 | 只有你配了才有；没配就全部 401 |

**你的网页地址不会变**，还是 `http://127.0.0.1:3080/?token=...`。
`/mcp/dsh-agent-control` 不是给你浏览器点的（用浏览器 GET 它会返回 405）。

两个 token 长得都像"一串随机字符"，但**毫无关系**：控制台那个是 dsh 的浏览器令牌，
插件那个是你自己配的。**别把控制台打印的 token 填进 `VOID_DSH_CONTROL_TOKEN`。**

#### 重启时的目录，决定插件有没有 token

dsh 会读两个 `.env`：

```text
<启动 dsh 的目录>/.env     ← 项目层
$DSH_HOME/.env             ← 用户层（DSH_HOME 为空时 = C:\Users\<你>\.dsh\.env）
```

`dsh plugin` **不读** `.env`（`bin.js` 里只有 profile 启动那条分支调用 `loadLayeredEnv`），
但**重启 profile 会读**。所以「装的时候在哪」不影响，「**重启的时候在哪**」才影响：

| 重启时的目录 | 读到哪个 `.env` | 结果 |
|---|---|---|
| `E:\project\star-sanctuary\Void` | `Void\.env` | ✅ 有 token |
| 其他目录（如 `C:\Users\admin`） | 只有 `$DSH_HOME\.env` | ⚠️ 若那个文件不存在 → token 未设置 → **所有请求 401** |

> **推荐做法：把 token 放到 `$DSH_HOME\.env`**，这样从任何目录启动都生效，不用记着 `cd`：
>
> ```powershell
> # DSH_HOME 为空时就是 C:\Users\<你>\.dsh\.env
> Set-Content -Path "$env:USERPROFILE\.dsh\.env" -Value "VOID_DSH_CONTROL_TOKEN=<长随机串>"
> ```
>
> 实测：token 只存在于 `$DSH_HOME\.env`、从 `C:\` 启动，MCP 握手返回 **200**；
> 错误 token 与不带 token 都返回 401。
>
> **`.env` 只够 DSH 自己用。** 客户端（Codex / Cursor 等）是独立进程，**不读 `.env`**，
> 必须另设 Windows 用户级环境变量，否则它们发不出凭据、所有请求 401。
> 两边分工见 §阶段 6 的「接客户端之前」，踩坑记录见 §29.10 ⑦。
>
> 顺带一条：进程环境变量的优先级**高于** `.env`，所以临时想换 token，直接 `export` 就能盖掉
> 文件里的值——但那只在你当前窗口有效，关掉就没了。

> **这一步会动到你正在用的环境。** 按仓库规则属于需要你先确认的操作，
> 不要没验证就做。做完如果不对，按 §25.7 关掉即可。

#### ⚠️ 设了 `DSH_HOME` 的窗口里，`dsh` 命令指向哪里

这是本章最隐蔽的一个坑，务必先读。它影响本节**所有** `dsh` 命令，不只是 `dsh web`。

**现象**：在设过 `$env:DSH_HOME` 的窗口里敲 `dsh web`，你以为会打开平时那个界面，
实际它去**试验环境**里找 `web`，找不到就**悄悄新建一个空白的**，然后启动 —— 里面没有
你的会话、工作区、插件，而且**默认还是绑 3080**，跟你正在跑的那个撞端口。

**原因**：`web`、`headless`、`acp`、`sdk`、`sdk-minimal` 这 5 个名字是 dsh 的
**出厂模板名**。`loadProfile()` 的逻辑是：

```js
const dir = resolveProfileDir(name, home);          // home 来自 DSH_HOME
if (!existsSync(join(dir, "package.json"))) {
  const template = PROFILE_TEMPLATES[name];
  if (template === void 0) throw new Error(`profile ${name} does not exist; ...`);
  initProfile(dir, template.bundles, template.patchReload);   // ← 静默自动创建
}
```

也就是说：**模板名会自动创建，非模板名才会报错**。实测：

| 在全新 home 里执行 | 结果 |
|---|---|
| `dsh --profile web --dump-config` | 静默创建 `profiles\web`，组合成功 |
| `dsh --profile headless / acp / sdk / sdk-minimal` | 同上，全部自动创建 |
| `dsh --profile lingbang --dump-config` | 报 `does not exist`，不会创建 |

`lingbang` 是我们自己起的名字，所以它安全；`web` 不是。

**规避办法**（任选其一）：

```powershell
# 办法一（最省心）：这个窗口专门跑隔离测试，正式操作全部另开窗口

# 办法二：用完就清掉，之后这个窗口恢复正常语义
Remove-Item Env:\DSH_HOME
"DSH_HOME = '$env:DSH_HOME'"     # 空 = 走真实 ~/.dsh

# 办法三：执行前先确认自己在哪个 home
"DSH_HOME = '$env:DSH_HOME'"
```

> **为什么 `dsh plugin add` 更危险**：它既不打印目标 home，也没有 `--dump-config` 那种
> 可见输出。在设了 `DSH_HOME` 的窗口里装插件，会静默装进试验环境，你会以为装好了、
> 实际正式环境一点没变。装正式环境前务必先 `"DSH_HOME = '$env:DSH_HOME'"` 确认一次。

#### 为什么一定要用 `.tgz` 文件，不能直接指文件夹

`dsh plugin add` 后面跟文件夹路径时，它只会放一个「快捷方式」过去。Node 找依赖时
是按真实位置往上找的，快捷方式那条路走不通，结果就是 DSH 启动直接报
`Cannot find package '@deepseek-ai/cordis'`。

用 `.tgz` 文件装，文件会被真正放进环境里，依赖就能找到。这是实测结论，详见 §20.3。

### 25.4 配置：每一项是干什么的

配置写在两个地方，作用不一样：

| 写在哪 | 文件 | 什么时候生效 |
|---|---|---|
| **A. 环境配置** | `$DSH_HOME\profiles\<环境名>\cordis.patch.yml` | 改完**要重启** DSH |
| **B. 用户设置** | `$DSH_HOME\settings.yaml` | 改完**立刻生效**，不用重启 |

能放到 B 的只有「给 AI 立的规矩」那几项（见下面表格里标了 **B** 的）。其余都必须放 A。

#### 全部配置项

| 配置项 | 通俗解释 | 默认值 | 放哪 |
|---|---|---|---|
| `enabled` | **总开关**。`false` = 窗口关闭，插件完全不工作 | `true` | A |
| `path` | 窗口开在哪个网址路径上 | `/mcp/dsh-agent-control` | A |
| `tokens` | **谁能进**。写的是「暗号存在哪个环境变量里」，不是暗号本身 | 一个叫 `default` 的客户，暗号变量 `VOID_DSH_CONTROL_TOKEN` | A |
| `allowAnonymous` | 不要暗号也能进。**只在你自己本机试的时候用** | `false` | A |
| `allowedRoots` | **允许碰哪些文件夹**。写绝对路径，可以写多个 | `[]`（空 = 完全不允许按路径指定文件夹） | A |
| `allowedOperations` | **允许办哪些业务**。客户没单独指定时用这一份 | 见 §25.5 | A |
| `ledger` | 记账存哪。`storage` = 存文件，重启还在；`memory` = 只在内存，重启就没 | `storage` | A |
| `callerInstructions` | **办事须知**。写给来访 AI 看的规则正文 | 空 | A + **B** |
| `requiredFields` | 下单时**必须填**的信息，比如 `objective` | `[]` | A + **B** |
| `requiredDocumentRules` | 下单时**必须附带的文档**，可以规定文件名格式 | `[]` | A + **B** |
| `forbiddenPatterns` | **违禁词**。内容里出现就拒绝，比如密钥特征串 | `[]` | A + **B** |
| `instructionsVersion` | 规矩的版本号。你改了规矩就加 1，方便对方确认拿到的是新版 | `0` | A + **B** |
| `callback` | **干完主动通知我**。见 §25.6 | 关闭 | A |

#### 三个最容易搞错的地方

1. **`allowedRoots` 留空 = 完全禁止。** 来访 AI 只能用你已经登记过的项目，
   不能自己指定路径。想让它能打开新项目，必须在这里写清楚允许哪些根目录。

2. **`cordis.patch.yml` 是一个列表，不是随便追加。** 文件原本长这样：

   ```yaml
   # 注释……
   []
   ```

   那个 `[]` 表示「空列表」。你要**把 `[]` 替换掉**，写成：

   ```yaml
   # 注释……
   - id: void-dsh-control
     config:
       enabled: true
       allowedRoots:
         - 'E:\work\my-project'
   ```

   直接在 `[]` 后面另起一行写 `- id:`，DSH 会启动失败并报
   `failed to parse overlay ... YAMLException`。

3. **写进去的 `config:` 会整块替换掉默认值。** 你只写 `enabled: false`，
   其余项就都回到默认值了。所以要么把要改的项写全，要么只写确实要改的。

### 25.5 权限与操作项

分两层：**权限**决定「允许办哪几类业务」，**操作项**是对方实际能调用的九个工具。

### 25.5.1 权限：允许对方办哪些业务

一共 10 种业务，名字和含义：

| 业务名 | 通俗解释 |
|---|---|
| `workspace.read` | 看有哪些项目、项目里有哪些对话 |
| `workspace.open` | 把一个文件夹登记成项目 |
| `session.list` | 列出对话 |
| `session.create` | 开一个新对话 |
| `session.prompt` | **给对话发消息**（最常用，等于「派活」） |
| `session.inject` | 往对话里塞点背景资料，但**不叫醒**它 |
| `session.steer` | 正在干活时插话改方向 |
| `session.observe` | 看对话的进度和状态 |
| `task.read` | 查自己派出去的活干到哪了 |
| `task.cancel` | 撤回派出去的活 |

**权限会自动带上需要的前置项**，你不用一个个列全：

| 你写了 | 自动也给它 |
|---|---|
| `session.prompt` | `session.create` → `workspace.read` |
| `session.inject` 或 `session.steer` | `session.create` → `workspace.read` |
| `workspace.open` | `workspace.read` |
| `task.cancel` | `task.read` → `session.observe` |

**常见配法：**

```yaml
# 只让看，不让动
operations: [workspace.read, session.list]

# 能派活、能查进度，不能撤回
operations: [session.prompt, task.read]

# 全能
operations: [workspace.read, workspace.open, session.list, session.create,
             session.prompt, session.inject, session.steer, session.observe,
             task.read, task.cancel]
```

想给不同客户不同权限，就写多个 `tokens`：

```yaml
tokens:
  - callerId: codex
    tokenEnv: CODEX_TOKEN
    operations: [session.prompt, task.read]
  - callerId: dashboard
    tokenEnv: DASHBOARD_TOKEN
    operations: [workspace.read, session.list]
```

### 25.5.2 操作项：对方能看到的九个工具

对方连上窗口后，能看到的九个「按钮」。每个按钮需要一种或几种上面的业务权限；
权限不够的按钮调了会被拒（`dsh-control/forbidden-operation`）。

| 工具名 | 通俗解释 | 需要哪种业务 |
|---|---|---|
| `dsh_control_info` | **看办事须知**。返回当前规则、必填项、各种上限、自己有哪些权限。对方开工前应该先点这个 | 只要能进门就行，不需要额外权限 |
| `dsh_dispatch_session_task` | **派一个活**。一步到位：找项目 → 开新对话或接着旧对话 → 把消息发进去 | `session.prompt` |
| `dsh_send_message` | **往已有对话里补一句话**。适合「接着上次那个对话继续」 | `session.prompt` |
| `dsh_inject_context` | **塞背景资料**。放进上下文但**不叫醒**对方；返回里会明确写「已注入、未执行」，别误以为活干了 | `session.inject` |
| `dsh_list_workspaces` | **看看有哪些项目** | `workspace.read` |
| `dsh_list_sessions` | **看看某个项目里有哪些对话** | `session.list` |
| `dsh_get_task` | **查这个活干到哪了**。返回当前状态和最近若干条进度 | `task.read` |
| `dsh_wait_task` | **守着等**。一直等到某个状态，或者等到超时。断线了可以带上上次的进度游标接着等，不会漏事件 | `task.read` |
| `dsh_cancel_task` | **撤回这个活**。只停掉对应的那一轮，**不删对话、不删项目、不删文件** | `task.cancel` |

还有一项不算按钮：`dsh://tasks/{任务号}/events`，是一个只读的「进度流水」地址，
支持读资源（Resource）的客户端可以直接订阅它。

#### 派活时对方要填什么

拿最常用的 `dsh_dispatch_session_task` 举例，对方要给你这些东西：

| 字段 | 通俗解释 | 必填 |
|---|---|---|
| `requestId` | 这单的编号，对方自己起。**同一个编号重复下单只会执行一次**（防手抖重复派活） | 是 |
| `target.workspace` | 去哪个项目。二选一：给项目编号 `workspaceId`，或给文件夹绝对路径 `path` | 是 |
| `target.session` | 用哪个对话。`"new"` = 开新的；给对话 id = 接着旧的 | 是 |
| `messages[].text` | 要说的话 | 是 |
| `messages[].mode` | `queue` = 排队等它有空；`steer` = 正在干活时插话改方向（要 `session.steer` 权限） | 否，默认 `queue` |
| `messages[].documentRefs` | 让它读的文档。`reference` = 只告诉它路径；`inline` = 把内容一起发过去 | 否 |
| `wait.until` | 等到哪个状态再回你。不填就立刻回「已受理」 | 否 |
| `wait.timeoutMs` | 最多等多久，上限 120 秒 | 否 |
| `metadata` | 给你自己查账用的信息。**模型看不到**——想让模型看到的内容必须写进 `messages[].text` | 否 |

#### 进度状态都有哪些

对方查进度时会看到这些词，按发生顺序：

| 状态 | 通俗解释 |
|---|---|
| `accepted` | 单子收了 |
| `workspace_resolved` | 项目找到了 |
| `session_created` / `session_resumed` | 新对话开好了 / 旧对话接上了 |
| `prompt_queued` | 消息排上队了 |
| `running` | 正在干活 |
| `assistant_message` | 它说了一段话 |
| `idle` | 这一轮干完了，闲着 |
| `completed` | **任务完成**（必须先看到 `running`，再看到 `idle`，才算真完成） |
| `failed` | 出错了 |
| `cancelled` | 被撤回了 |

最后三个是「终态」，到了就不会再变。

### 25.6 让 DSH 干完活主动通知你（可选）

有些客户（比如一个后台脚本）不方便一直守着问「干完了吗」。可以让 DSH 干完主动
发一个 HTTP 请求过去。默认关闭。

```yaml
- id: void-dsh-control
  config:
    callback:
      enabled: true
      url: 'https://你的接收地址/hook'
      secretEnv: VOID_DSH_CONTROL_CALLBACK_SECRET
      events: [completed, failed, cancelled]
      timeoutMs: 10000
      maxAttempts: 5
      allowedHosts: ['你的接收地址的域名']
      includeAssistantSummary: false
```

```powershell
$env:VOID_DSH_CONTROL_CALLBACK_SECRET = "另一个长随机串"
```

| 项 | 通俗解释 |
|---|---|
| `url` | 通知发到哪。**只能你自己在这里写死**，外人不能临时指定 |
| `secretEnv` | 签名密钥存在哪个环境变量里 |
| `events` | 哪些情况要通知：干完了 / 失败了 / 被撤回了 |
| `timeoutMs` | 等对方回应最多等多久 |
| `maxAttempts` | 对方没接住就重试几次（间隔 1 秒、2 秒、4 秒……最多 1 分钟一次） |
| `allowedHosts` | 地址域名白名单。写了就强制检查，防止配错地址 |
| `includeAssistantSummary` | 要不要把**模型写出来的文字**一起发过去。默认不发 |

发过去的内容只有任务摘要和进度游标，**不会发整段对话记录**。
每条通知都带一个签名（`x-dsh-control-signature`），接收方可以验真伪、防重放。
对方重复收到同一条也没关系——带 `deliveryId`，按它去重即可。

### 26.1 P1 功能与安全问题

1. **路径 Workspace 绕过 `workspace.open` 权限**：`dsh_dispatch_session_task` 统一只校验 `session.prompt`，当 target 使用绝对路径时没有追加 `workspace.open` 检查。拥有 prompt 权限的调用方可以登记 `allowedRoots` 内的新 Workspace，违反 §7.1、§11 和场景 A 的最小权限要求。涉及 `src/mcp.ts` 的 dispatch 处理和 `src/orchestrator.ts` 的 `TOOL_OPERATIONS`。
2. **文档引用允许 `..` 穿越**：`src/workspace.ts` 的 `assertPathInsideWorkspace()` 先将相对路径解析后再判断 allowed root；因此 `../outside/file` 只要落入其他 allowed root 就会通过，并以 `../...` 形式传给 Agent。§8.2、§11 和场景 G 要求拒绝 `..` 穿越；只有明确的绝对路径才允许使用额外 allowed root。
3. **幂等检查存在 TOCTOU 竞态**：`dispatch()` / `sendMessage()` 先读取幂等表，经过多个 `await` 后才由 `createTask()` 写入保留键。同一调用方并发使用同一 `requestId` 时可能创建两个任务并重复投递消息，违反 §6.1、§10.2 和场景 D。需要进程内 key mutex 或原子 reserve 语义。
4. **Session 任务锁与事件归属错误**：已有任务持锁时普通 queue 仍会被放行，随后 `attachSession()` 无条件覆盖 `sessionToTask`。后续 running/idle 事件可能归属后一个任务，原任务无法完成或释放锁；这也违反 §7.3 中“有任务锁时不允许其他外部任务竞争”的约束。
5. **Webhook 回调阻塞编排主流程**：`WebhookCallbackDispatcher.onTaskEvent()` 等待网络重试链，编排器的 `record()` 又等待该观察者。回调超时或退避会阻塞任务状态推进，与 §9.2 和 §12 要求的非阻塞通知相反。回调应 fire-and-forget，账本写入和状态机推进不能等待远端 HTTP。
6. **插件卸载没有等待在途任务**：disposer 只调用 `stopAccepting()`，随后注销路由、等待 callback 并关闭 ledger；已经接纳的编排操作仍可能继续写存储，形成关闭后的写入竞态。需要增加 orchestrator drain/quiesce，并在关闭 ledger 前等待所有 admission chain 收敛，符合 §12、§16。
7. **重启恢复不完整**：`StorageControlLedger.init()` 将所有非终态任务直接标记为 failed，没有按 §10.3 查询 Session 日志或队列判断消息是否已经接收；`callback_deliveries` 中 pending 记录也没有在启动后恢复投递。可能造成已接收任务被错误标失败、未送达回调永久丢失。

### 27.4 修复引入的行为变更（使用者可见）

这几条是**故意**的行为变化，升级后按新行为理解：

1. **同一 Session 同时只允许一个外部任务。** 以前 `queue` 消息能在别人持锁时挤进去
   （并因此抢走事件归属、让原任务悬挂）；现在 `queue` 和 `steer` 一样会被
   `dsh-control/session-locked` 拒绝。§7.3 的原文就是「普通消息可以在**没有任务锁**时排队」。
2. **`dsh_inject_context` 不再成为 Session 的事件归属者。** 注入本来就不唤醒 Agent，
   让它占住归属会让真正在跑的任务收不到 running/idle。
3. **相对文档引用不能再用 `..` 逃出工作区。** 要引用别的 `allowedRoots` 下的文件，
   必须写绝对路径。
4. **按绝对路径下单需要 `workspace.open`。** 只有 `session.prompt` 的 token 仍可用
   `workspaceId` 给已登记项目下单。
5. **重启后的孤儿任务会说明「消息是否已投递」。** 已投递的会明确写「Agent 可能在控制面之外
   继续或完成了这项工作」，不再一律说成「没发生过」。

## 28. Token 配置可发现性改进与保留方案（2026-09-20）

起因：把插件装进正式 `web` profile 并重启后，MCP 端点对所有请求返回 401，但**用户完全
不知道原因**——终端上没有任何提示。本节记录根因、本轮改动，以及一个已评估但**未采纳**
的设计方案。

### 28.1 根因：插件警告到不了终端

插件本来就 `log.warn()` 了两条：

```text
token environment variable VOID_DSH_CONTROL_TOKEN is unset; that caller cannot authenticate
no usable machine token and allowAnonymous is false: every request will be rejected with 401
```

但它们在终端上**看不见**。原因是 Cordis 的 `LoggerService` 默认只挂了一个 sink：

```js
self.exporter({
  colors: 3,
  export: (message) => { self.buffer.push(message); /* 只进 1000 条环形缓冲 */ }
});
```

实测全树扫描 `node_modules/@deepseek-ai/**/*.js` 里的 `.exporter(`，只有两处：

| 位置 | 作用 |
|---|---|
| `@deepseek-ai/cordis/lib/index.js` | 内存环形缓冲（默认 sink） |
| `@deepseek-ai/dsh-web-frontend/dist/assets/index-*.js` | 浏览器端，从缓冲取数据渲染 Web UI 日志面板 |

**Node 侧没有任何 console exporter。** 所以插件日志只进 Web UI 的日志面板，
坐在终端前的操作者看不到——「不知道为什么会 401」是必然结果，不是用户疏忽。

启动时终端上那几行（`dsh web: http://...`、chrome-devtools-mcp 横幅）都不是 `ctx.logger`
的输出：前者是启动器直接 `process.stdout.write`，后者是那个插件自己写 stderr。

### 28.2 本轮改动

| 改动 | 位置 | 说明 |
|---|---|---|
| 新增 `userEnvFilePath(env?)` | `src/auth.ts` | 复刻 `resolveDshHome()` 的解析（`DSH_HOME` 非空优先，否则 `~/.dsh`，支持 `~` 前缀），算出用户级 `.env` 的真实路径。刻意用复刻而非新增 peer 依赖：这段提示只是建议性质，多一个 peer 会多一条版本契约和每次安装都出现的 peer 警告 |
| 新增 `describeTokenSetup(missingEnv, envFile)` | `src/auth.ts` | 纯函数，产出「诊断 + 可直接复制的修复命令 + 文档指针」多行文本。**绝不包含也不生成 token 值** |
| 双 sink 输出 | `src/index.ts` | `log.warn(guidance)` 进 Web UI 日志面板；同时按行加 `[void-dsh-control] ` 前缀直写 `process.stderr`。先例：dsh 自己的 `loadLayeredEnv` 就把启动期配置错误直写 stderr（`warn = (line) => void process.stderr.write(line)`）。只在「无任何可用 token 且未开 `allowAnonymous`」时触发，即端点完全不可用的那一种情况 |
| 文档第三步重写 | 本文档 §25.3 | 从「export 一个变量」改为「一条命令生成强随机暗号并写进 `$DSH_HOME\.env`」，并说明为什么推荐用户级位置（与启动目录无关） |

真实启动时的终端输出（隔离 profile，无 `.env`）：

```text
[void-dsh-control] no usable machine token (VOID_DSH_CONTROL_TOKEN unset) and allowAnonymous is false:
[void-dsh-control] every request to the control endpoint will be rejected with 401
[void-dsh-control]   fix it once — dsh reads this file no matter which directory it is launched from:
[void-dsh-control]     $t = -join ((48..57)+(65..90)+(97..122) | Get-Random -Count 48 | ForEach-Object { [char]$_ })
[void-dsh-control]     Add-Content "C:\Users\<你>\.dsh\.env" "VOID_DSH_CONTROL_TOKEN=$t"
[void-dsh-control]   then restart dsh; full procedure: docs/灵榜会话功能实现方案计划.md §25.3
```

### 28.3 跨平台：WSL / Linux / macOS

首次实现只印了 PowerShell 方言的修复命令，这在 WSL 里是错的——WSL 下 dsh 是 **Linux 进程**，
操作者敲的是 bash，既没有 `$env:USERPROFILE` 也没有 `Add-Content`。

| 方面 | 结论 |
|---|---|
| 路径解析 | ✅ 本来就对。`node:path` 是平台原生的，Linux 下走 posix 语义，`userEnvFilePath()` 返回 `/home/<你>/.dsh/.env` |
| 修复命令方言 | ❌ 原实现只有 PowerShell。已改为按 `process.platform` 选择：`win32` 印 PowerShell，其余印 POSIX shell |
| POSIX 生成命令 | `t=$(od -An -tx1 -N32 /dev/urandom \| tr -d ' \n')` —— `od`/`tr` 是 POSIX 标配，不依赖 openssl 或 python |
| 目录创建 | POSIX 分支带 `mkdir -p`：全新的 WSL home 里可能还没有 `~/.dsh`，`>>` 会失败或建错位置 |
| 两个系统各装一套 | Windows 读 `C:\Users\<你>\.dsh\.env`，WSL 读 `/home/<你>/.dsh\.env`，是**两个不同文件**，哪边跑就在哪边配 |

### 28.4 保留方案：`generateTokenOnFirstBoot`（已评估，未采纳）

**提议内容**：正式安装时若 `$DSH_HOME\.env` 不存在，则自动创建并填入一个默认暗号
（当时举的例子是 `888888`），类比「银行卡初始密码」。

**评估结论**：位置选得对，机制和默认值都不采纳。三条理由：

1. **时机做不到。** `dsh plugin add` 是 dsh 自己的命令，插件代码只在 profile **启动**时
   执行，所以"安装时"没有任何本插件的代码在跑。若改到"首次启动时创建"，则每次启动都
   成为一次隐式写盘，且与 §11 已定的契约（token 只从环境变量读、不写入任何文件）直接冲突。
2. **默认值会把响亮的失败换成安静的失败。** 无 token → 401 → 用户去查 → 配好强暗号，
   一次麻烦换长期安全；有默认值 → 立刻可用 → 用户再也不会看 → 永久弱凭据。而银行卡
   初始密码依赖物理介质、单独渠道送达、首次使用常强制改密，这些约束在这里都不存在——
   loopback 上任何本机进程都能试。**固定默认值比没有暗号更危险**，因为它看起来像配好了。
3. **便利性收益有限。** 用户无论如何都要把暗号**读出来填进 Codex 的配置**，"生成"省掉了、
   "读取"省不掉。

**若将来要做，可接受的形态**（仍不推荐默认开启）：

- 配置项 `generateTokenOnFirstBoot`，**默认 `false`**，用户显式开启才写盘；
- 写的是**每次随机**生成的值（不是固定值），并在启动日志与 stderr 各打印一次（Jupyter 风格）；
- 写入前检查目标文件是否已存在同名键，绝不覆盖已有暗号；
- 明确文档化为「降低首次配置门槛」而非「默认安全」。

其他候选方向（尚未评估）：Windows DPAPI / 系统凭据管理器托管、由 `dsh plugin` 侧提供
配置向导、Web UI 里加一个「生成并写入」按钮。

## 29. 虚空（Void）面板配置化改造方案（2026-09-20）

§28 之后，用户已把 `@void/void-entry` 装进正式 `web` profile，设置页左侧出现了
**「虚空（Void）」**栏目，能列出该 profile 里已安装的 Void 插件。本章要把它从「插件清单」
升级为**配置面板**：让用户在界面里配置本插件的**全部配置项**与 §25.5.1 的**权限**。

> 本章是**实现方案与四期计划**。面板本身的布局改造属于 Void 套装入口（`void-entry`），
> 但其配置对象是灵榜控制面，故方案落在此文档；`虚空寄生实施方案计划.md` 留有指针。

### 29.1 侦察结论（在 dsh `0.1.5-rc.2` 上实测，非推测）

**① 配置写回通道已经存在，模型面板用的就是它。**

| 调用 | 用途 |
|---|---|
| `ctx.remote.settings.describe()` | 列出全部已注册 namespace：**序列化 schema + 脱敏值 + revision** |
| `ctx.remote.settings.update(ns, patch, rev)` | 合并写入用户层，**热生效** |
| `ctx.remote.settings.replace(ns, section, rev)` | 整体替换用户层 section |
| `ctx.remote.settings.mutate(ns, ops, rev)` | 路径寻址操作 |
| `ctx.remote.credentials.set/unset` | 密钥**单向**写入（任何读路径都不返回值） |

返回值是 `RemoteResult<T>` = `{ok:true,value}` 或 `{ok:false,error}`。并发冲突有专门错误码
`settings/conflict`（details 带 `expected` / `actual`）——**陈旧编辑器会被拒绝，而不是静默
覆盖**，调用方需重新读取后再提交。

依据：`@deepseek-ai/dsh-api-settings-controller` 的 `typert.remote-client.d.ts` 生成签名；
`@deepseek-ai/dsh-client-ui-settings-models` 实际调用 `remote.settings.mutate` +
`remote.credentials.describe/set/unset`。`@deepseek-ai/dsh-settings` 的
`SettingsNamespaceView` 定义了 wire 视图（`ns` / `schema` / `value` / `base` / `user` /
`applies` / `secrets` / `revision`）。

**② 宿主提供的 UI 原语：202 个导出，但组件很少。**

客户端 bundle 可 `require()` 的宿主模块共 5 个（`cordis`、`dsh-client-store`、
`dsh-client-ui-slots`、`dsh-client-ui-primitives`、`dsh-client-ui-dockkit`）。
`ui-primitives` 里可用的组件：

| 类别 | 清单 |
|---|---|
| 交互 | `Button` `Menu` `Switch` `Input` `SearchBlock` |
| 容器/浮层 | `DisclosureRow` `Modal` `Tooltip` `HoverCard` |
| 展示 | `Pill` `Tag` `StateDot` `ConnectionIndicator` `RiskConfirmation` `OnboardingSurface` `MarkdownText` `CodeBlock` `JsonTree` |
| 图标 | **`Icon*` 共 75 个** |
| **没有** | Card / Tabs / Select / Textarea / Table / Checkbox / Form —— 需自写 CSS |

`dshmarket`（插件市场）就是这么做的：自写卡片与标签页 CSS，交互控件用宿主原语，并在
`apply()` 里用 `missingPrimitives()` 检查 `Menu` / `DisclosureRow` / `Tooltip` / `Toast`
是否存在，缺失就**整体不注册**（干净降级），避免渲染抛错把整个设置弹窗弄白。本方案照搬
这个守卫模式。

**③ 现状缺口：面板改不到大部分配置。**

`void-dsh-control` 目前只把 **5 个**字段注册进 settings（`settings.register("dsh-agent-control", ...)`）：

```text
已可配    callerInstructions / requiredFields / requiredDocumentRules
          / forbiddenPatterns / instructionsVersion
改不到    enabled / transport / path / tokens / allowAnonymous / allowedRoots
          / allowedOperations / ledger / callback.*
```

后者全部来自**组合入口**（`cordis.patch.yml` 的 entry config）。面板要能配它们，必须先把
注册进 settings 的 schema 扩到覆盖全量。

### 29.2 核心设计决策

**不自建配置存储。** 把 `void-dsh-control` 的配置整体注册成一个 settings namespace，面板
通过 `ctx.remote.settings` 读写。这样白拿三件事：**热生效**、**revision 防并发覆盖**、
**密钥脱敏**——与模型面板同一套机制，不引入第二套配置语义。

**面板做成通用 schema 渲染器**，而不是给灵榜写死界面：

```text
void-dsh-control (host)        void-entry (host)           void-entry (client)
  settings.register(ns, schema)  →  展示清单（分组/中文标签）  →  describe()
                                     /void/api/panels             → 按 schema 渲染表单
                                                                  → update(ns, patch, rev)
```

收益：**新插件只要注册了 settings namespace，零改动就出现在面板里**。展示清单只负责
「怎么分组、叫什么中文名」，缺失时退化为 schema 字段顺序 + 字段名。

**分层语义**（沿用 `ctx.settings` 既有定义）：schema 默认值 < 组合入口 `base` < 用户层。
即用户没配过的字段仍由 `cordis.patch.yml` 决定，面板写入只覆盖用户层——**回滚只需删掉
用户层那几行**，与 §25.7 的回滚路径一致。

### 29.5 权限矩阵设计

数据源是 §25.5.1 的 10 种业务与自动前置表。界面要点：

### 29.6 密钥处理

`tokens[].tokenEnv` 是**变量名**，可以进 settings；**token 的值绝不进配置**（§11 的既定
契约：token 只从环境变量读，不写入任何文件）。

面板显示：

```text
调用方 codex        tokenEnv  [CODEX_TOKEN          ]
                    ● 已设置（来自 .env）     [重新生成]
```

「已设置」由 host 半边读 `process.env` 得出，**只回一个布尔**，值不过线。这与宿主
`SettingsNamespaceView.secrets` 的设计意图一致（`role('secret')` 字段不随 wire 出行）。

重新生成按钮不直接写 `.env`（§28.4 已论证过自动写盘的风险），而是给出与
`describeTokenSetup` 同一份的命令文本，由用户自行执行。

*注册面*：`PolicySection`（5 字段）扩为 `ControlSection`（10 字段），`createPolicySource` 换成
`createConfigSource`，一次性返回四个访问器：`live()` / `policy()` / `auth()` / `watch()`。
`policy()` 与 `auth()` 各自按原始值做记忆化，所以热路径上不会重复编译正则或重复解析操作名。

*刻意不纳入的四个字段*：`enabled` / `transport` / `path` / `ledger`。它们决定插件是否装载、
挂在哪条路径、用哪个账本，属**组合入口**职责；dsh 的 settings 服务每个 namespace 只能声明
一个 `applies`，混进来要么被错标为 live，要么把整节标成 restart-only。面板改为只读展示 +
指向配置文件（§29.4）。**即"全部配置项"里有 4 项是"可见可查、不可热改"**，这是如实划分，
不是遗漏。

*把固定值改成提供者*（热生效的关键）：

| 位置 | 改动 |
|---|---|

| `guard` | `allowedRoots` 是唯一需要异步的字段（`realpath`），故启动时解析成快照，`source.watch()` 触发时重算；HTTP 守卫读快照，保持同步 |

**实施记录（2026-09-20）**

*清单由插件自己贡献*。原本可以让 `void-entry` 维护一张涵盖所有插件的大表，但字段标签、
控件选择、尤其**权限前置关系**都是插件自己的知识——放两处必然失同步。改为入口发布
`registerPanel(packageName, manifest)`，各插件在自己的 `ctx.inject(["voidSuite"], ...)`
里贡献（`void-dsh-control/src/panel.ts`）。装在没有 `void-entry` 的 profile 里时该服务
不存在，回调不执行，插件其余功能不受影响。

*前置关系下发传递闭包*。先写了 `OPERATION_PREREQUISITES` 想自己维护一张表，**核对时发现
写错了**：运行时的 `OPERATION_IMPLICATIONS` 是**直接**蕴含表（`session.observe: []`、
`task.read: []`），我按传递闭包凭印象写，`session.list` / `session.observe` / `task.read`
三项都不对。这正是 §29.5 警告过的「不在 UI 里重写一份」。改为清单里直接下发
`expandOperations([value])` 的输出（传递闭包），客户端只做集合并集，**没有任何图运算**，
因此没有机会算错。

*新增文件*：`src/client/remote.ts`（宿主 settings Remote 的客户端，协议实测得出而非猜的）、
`src/client/controls.tsx`（schema 驱动的控件层）。`src/client/index.tsx` 改为通用渲染器。

*写回语义*：`settings/mutate` + `expectedRevision`。被 `settings/conflict` 拒绝时**重新读取
并提示用户重试**，而不是重试写入——后者会把别处的改动盖掉。文本类控件本地存草稿、失焦才
提交：每敲一个字发一次写回会打乱 revision，也会让服务端校验在用户还没写完时就报错。

*只读字段*：`enabled` / `path` / `ledger` / `transport` 四个组合入口字段在清单里标

### 29.10 按官方文档对齐（2026-09-20）

查 `deepseek-harness` 官方文档时发现三处我们与官方机制不一致或需要收口的地方。

#### ① `createConfigSource` → 官方 `ctx.settings.installSection()`

官方 `docs/cookbook/adding-a-settings-card.zh.md` 原文：「已经有 `cordis.yml` entry 的消费方
**应**通过 `ctx.settings.installSection()` 注册——它把 entry 层叠在用户文档之下，并在没有挂载
settings provider 时照常工作」。核 rc.2 类型定义，它早就在。我们此前手搓的等价物：

| | 官方 `installSection` | 改前 |
|---|---|---|
| entry 作 base 层 | 内置 | 手写 `register({ base: entry })` |
| provider 缺失时回落 | 内置 | 手写 `read = () => entry` |
| provider **后于插件**挂载 | `ctx.inject` 响应式采纳 | `ctx.get("settings")` **apply 时一次性判断，此后永不重试** |
| provider 卸载 | 回落 entry | 无 |
| 变更通知 | `onChange()`（attach / detach / 提交后各一次） | `scope.watch()`（只在提交后） |

官方范例（`dsh-bash-local`）只有三行实质代码——`this.source = () => entry`、
`ctx.inject(['settings'], cb)`、`installSection(..., { setSource })`——`onChange` 甚至是空函数。

改动：`ConfigSource` 去掉 `registered`，`watch` 改为订阅「attach / detach / 提交」三类事件；
`SETTINGS_NAMESPACE` 提为常量；`ctx.get("settings")` 探测只剩一条日志判断。

**唯一行为增强**：provider 后挂载也能被采纳。这条单独写了用例
（`settings.spec.ts` → "adopts a settings provider that attaches after the plugin is composed"）。
写这个用例时发现 `ctx.inject` 回调**不是同步执行**的——发布服务后要给一个 tick，这点记在
用例注释里，免得后人以为是多余的等待。

测试替身 `FakeSettings` 相应补了 `installSection`（含 attach 时 `setSource` + `onChange`、
owner 卸载时回落 entry 并注销命名空间），并删掉 `register`；`register` 我们已无人调用。

**真机验证**（隔离 profile，端口 3699）：面板改「调用约束正文」→ 写入 `settings.yaml` →
**MCP 端点 `dsh_control_info` 返回新值**。失焦提交行为未被破坏（输入 0 次写回、失焦 1 次）。

#### ② 面板从「即时写」改成官方的「暂存 + 保存」

官方 `packages/client/ui-settings-plugins/README.zh.md` 的规则：「页面暂存用户输入，**只有
用户保存时才写入**」「每次单字段写入或有序 mutation 都以**草稿读取时的命名空间 revision
设栅**」「保存失败时页面保持原样、报告失败并**保留草稿**」「**字段不接受的草稿会阻塞保存**，
而不是被丢弃」。

**这一条修正了我们对 P4 那个 bug 的判断。** 当时把「每敲一个字就提交」当成控件级疏忽，
用失焦提交逐个控件修好了。但根因是**架构上缺一层草稿**：没有草稿层时任何输入都必须立刻
变成一次写回，于是每个控件都得各自想办法避免半成品值上线——而想不周全的地方就会漏。
补上草稿层之后，输入根本不碰写回，那一整类问题从结构上消失了。

**实现**：草稿逻辑集中在新的 `void-entry/src/client/draft.ts`（纯函数，16 例单测覆盖），
界面只负责调用。

- `Draft = { values: Record<pathKey, unknown>; revision }`，`revision` 取**首次编辑时**读到的
  值，中途别处的改动不跟着更新——否则设栅就失去意义。
- 卡片正文顶部有常驻保存条：有草稿时出现，带「保存 / 放弃」，有阻塞项时禁用保存并说明原因。
- 保存只发出**真正变了**的字段：把没动的也写一遍会平白抬高 revision，让别人的编辑器无谓冲突。
- 保存失败**保留草稿**；冲突时重读并把设栅推到新 revision，让用户核对后再存——不替他重试。
- 「放弃」把字段还原成服务端值。官方那边「离开页面即丢弃草稿，没有放弃控件」，我们**多给了
  一个显式放弃**——丢掉用户没保存的东西比多一个按钮糟。

**改这一项时抓出的 bug**：`TextField` 和 `NumberField` 自己攒着本地草稿、**失焦才上报**。
我在列表编辑器里去掉了这层延迟，漏了这两个，结果「改完立刻点保存」提交的是改动前的值，
而且保存条根本不出现（改动没进草稿）。真机上表现为「输入后保存条不出现」——开关控件却是
正常的，靠这个差异定位到是文本路径特有的问题。空 id 规则的拦截也从「失焦时跳过提交」挪到
了保存前的阻塞检查，落在 `saveBlockers` 里并有单测。

**同步简化**：`useDraftArray`（P4 为失焦提交而引入的带状态 hook）删除，换成无状态的
`listEditor`；空行过滤从「提交时清」挪到 `sanitizeForSave`，因为「点添加」产生的空行本来
就只是草稿的一部分。

**真机验证**（隔离 profile，端口 3699）：

| 动作 | 写回次数 | 结果 |
|---|---|---|
| 输入 8 个字符 | **0** | 保存条出现、字段标「未保存」 |
| 失焦 | **0**（改前是 1） | — |
| 点保存 | **1** | 落盘 `settings.yaml`，MCP 端点返回新值 |
| 改完点放弃 | **0** | 字段**还原**成服务端值 |
| 加一条空 id 规则 | 0 | 显示「没填 id」，**保存按钮禁用** |

`void-entry` 6 文件 / 55 例（新增 16 例覆盖草稿、规整、阻塞、操作生成），三层 typecheck 全绿。
#### ③ 已确认无需改的三项

| 项 | 结论 |
|---|---|
| DSH 有没有一等公民的 MCP **server** 注册点 | **没有**。官方包只有 `dsh-mcp-client`（DSH 作客户端消费外部 MCP），无 server 侧；`webhookRuntime` 是入站 webhook（GitHub 那类），不是 MCP。我们经 `ctx.webServer.register()` 挂路由是**唯一且正确**的做法 |
| 官方插件卡 `settings.plugin.item` | 与我们用的 `settings.section`（侧栏分区）是**并存的两种表面**，不冲突。官方那套按命名空间自动配对 host/client 两半，我们那套是独立顶层分区 |
| 客户端 bundle 纯净度门禁 | 拒绝**跨插件值导入**；我们引的 `dsh-client-ui-primitives` 是宿主 5 个平台模块之一，合法。官方也明说「没有已发布的预设暴露该包，因此本仓库之外的包得自行复刻同样的输出格式」——印证手搓 tsdown 是必然 |

#### ④ `primitives.d.ts` 改为生成，不再手抄

**问题**：这个文件是编译期的 ambient 声明——`dsh-client-ui-primitives` 不能装进
`node_modules`（peer 会顶掉 workspace 的 cordis 4.0.1，见 §20.1），运行时由宿主冻结模块表
提供。手抄的后果是**会漂移且不报错**：宿主改了原语签名，本地声明不会跟上，要等真机渲染
崩了才发现。dsh 官方对同类问题用 `ts type-equiv` 门禁（文档里的类型声明必须与源码逐字
相等），`scripts/gen-primitives-types.mjs` 是它在「宿主外部包」场景下的等价物。

**设计：输入是用法，不是白名单。** 脚本扫描 `src/client/**` 里从该模块 import 的名字，
只生成这些；声明里引用到的包内类型按 import 与同文件引用递归带上。新用一个原语而忘了
重新生成，`pnpm run check:primitives` 立刻失败。

**接线**：`pnpm run gen:primitives` 生成，`pnpm run check:primitives` 校验（落后则退出码
1）。默认从 npm `pack` 同版包取类型，`--from <dir>` 可离线。

**两个只有关掉 `skipLibCheck` 才能发现的缺陷**——这一段是本次最有价值的部分：

1. **手抄版漏了 `ButtonVariant`。** `Button` 的签名里写着 `variant?: ButtonVariant`，而这个
   类型从未被声明过。`skipLibCheck: true`（在 `tsconfig.base.json` 里）让 `.d.ts` 内部的
   悬空引用**静默通过**，所以从 P1 起一直没被发现。
2. **生成器第一版产出了 `export declare function`。** 在 `declare module` 里已经是 ambient
   上下文，这个修饰符会报 TS1038。手抄版用的是 `export function`，是对的——**这个回归是

#### ⑦ 面板配方加「前提框」，并把 Codex 的两个坑写死（2026-09-20，用户实测踩出）

用户在真机接 Codex 时踩了两个坑，都写进配方了。

**坑一：`bearer_token_env_var` 填的是变量名，不是暗号本身。**

用户把 `bearer_token_env_var = "VOID_DSH_CONTROL_TOKEN"` 填成了

|---|---|
| 不存在 | ✅ 点名 |
| = 真实值 | ❌ 不点名 |
| = **错误值** | ❌ **不点名** |
| = 空串 | ✅ 点名 |

所以「doctor 干净」≠「能连上」，从诊断输出上看不出是这里错了。

**坑二：改用 `bearer_token` 明文字段会让整份配置加载失败。**

我一度建议用户改用它「省掉环境变量这层」——**这个建议是错的**。实测：

```
Caused by:
```

#### 真凶找到并修好了：账本并发的「先读后写」丢事件（2026-09-20）

上一节那个「未解释的矛盾」（能到 `completed` 却没有 `running` 事件）查清了。

**根因在两处同类的 read-modify-write 竞争**，都由「派发方以 `void` 调用、同一回合的信号并发执行」触发：

**① `StorageControlLedger.appendEvent()` 用条数分配 seq**（`ledger.ts`）：

```ts
const nextSeq = this.countEvents(event.taskId);   // 读
await table.put(eventKey(event.taskId, nextSeq), stored);   // 写 —— 中间隔着 await
```

两个并发追加读到同一个条数 → 写同一个 key → **后写的静默覆盖先写的**。

**内存实现没这个问题**，因为它的读和写在同一个同步块里（`list.length` → `list.push`，中间没有 `await`），
JS 单线程保证原子。**这就是为什么测试全绿而生产出问题：测试用 `MemoryControlLedger`，生产用
`StorageControlLedger`（bundle 里 `ledger: storage`）。**

**② `orchestrator.record()` 基于旧投影写回**：它「同步读 `current` → await 追加事件 → 写回
`{...current, ...}`」，两个并发调用都基于同一份旧投影，后写的抹掉先写的字段——`assistantSummary`
就在这条路径上。

**这两条恰好解释了之前所有反常现象**：`sawRunning` 在 `await` **之前**置位，所以任务照常走到
`completed`；而 `running` 事件在落盘时被覆盖，看起来像「信号从未到达」。

**修法**（按 taskId / sessionId 分桶串行化，两个问题一起消掉）：

- `StorageControlLedger` 加 `appendChains`，同一任务的 `appendEvent` 排队执行；
- `ControlOrchestrator` 加 `signalChains`，同一 Session 的 `applySignal` 逐条按序执行——
  这也顺带修正了状态机可能看到乱序信号的问题。

**测试**（`void-dsh-control` 13 文件 / 257 例，+3）：

- `ledger.spec.ts` 加两例：4 个并发追加必须各得不同 seq（**修复前实测只剩 1 条**）；交叉任务
  的 seq 必须各自稠密且不串台。
- `orchestrator.spec.ts` 加一例：并发信号必须按序、且 `assistantSummary` 不得被抹掉。
  **这一例第一次写成了假锁**——用 `MemoryControlLedger` 时竞争窗口被微任务顺序掩盖，
  未修复也照样通过；改成注入延迟的 `SlowAppendLedger` 后才真正会红
  （实测未修复时报 `expected undefined to be 'OK'`）。

**真机验证**（隔离环境，与生产同配置 `ledger: storage`）：

| | 事件序列 |
|---|---|
| 修复前 | `… session_created → prompt_queued → idle → completed`（**无 `running`、无 `assistant_message`**） |
| 修复后 | `… session_created → running → prompt_queued → running → **assistant_message** → idle → completed` |

- 新建 Session 与复用已有 Session **两条路径都通过**；

**未验证**：尚未在正式 `web` profile 复测（已装好，需重启）。隔离环境与生产同配置，预期一致。

#### 附带发现：用户层 patch 的 `config` 是整体替换，不是深合并

比对、哈希确认换掉）。复测结果**一好一坏**：


**M1 没修好 ❌，而且很可能是这次改动引入的回退。** 两条路径都复测了，账本里都**没有**
`assistant_message`：

| 任务 | 时间 | 代码 | 会话 | 结果 |
|---|---|---|---|---|
| `task-mu9pwbnq-4` | 11:12Z | **旧**（无 `global`） | `session_resumed` 已有会话 | ✅ seq 4 有 `assistant_message` |

排除掉的可能：

- **不是模型没回复。** Session 自己的统计是 `turns: 1, steps: 1, decodeTokens: 2`、
  `outputTokens: 2`——模型输出了 2 个 token（就是让回的「OK」）。1.7 秒完成是因为回复只有两个字。
- **不是 `global` 选项不被支持。** cordis 的 `EventsService.dispatch()` 是
  `filter((hook) => hook.global || !filter || filter.call(thisArg, hook.ctx))`，`register()` 也把
  `options` 正确展开进了 hook。`global: true` 语义上只会让监听器被调用得**更多**。

（`orchestrator.ts:539`，`signal.status === "running"` 时）。所以必然有 `running` 信号被
`applySignal` 收到过——但账本里**没有** `running` 事件。`record()` 不做转移校验、只追加，
所以它若被调用就必然留下记录。这条矛盾说明在 `sawRunning` 置位与 `record()` 落盘之间出了问题

`void ...` 调用的、异常无人接）。

**下一步**：在隔离环境里给 `applySignal` 加上落盘前的日志，跑一次任务，确认

### 29.12 DSH 原生计划模式入口与灵榜可行性（2026-09-20）

#### 入口核查

在 `参考项目/deepseek-harness-dsh-v0.1.6-alpha.2` 全仓执行
`rg -n -S "create_plan|enter_plan_mode"`，结果为 `NO_MATCH`。这两个名字不是 DSH 的
原生入口。alpha.2 的实际入口有三条：

- 人类命令 `/plan [message]`：`packages/plan/plan-mode/src/index.ts:225-270` 注册，处理器调用
  `PlanModeController.set(agent, true)`，有消息时再调用 `agent.steer(...)`；
- 服务接口 `ctx.planMode.set(agent, active)`：`packages/plan/plan-mode/src/index.ts:392-434`；
- 模型出口 `exit_plan_mode`：`packages/plan/plan-mode/src/index.ts:273-361`。它只负责提交完整计划
  并请求用户评审，不能在未激活模式时充当入口。

`packages/api/session-controller/src/commands.ts:299-370` 的 `sessionController.prompt()` 只把文本
包装成用户消息后走 `agent.followup()` 或 `agent.steer()`，不解析 `/plan`。Web 使用的命令通道在
`packages/api/session-controller/src/client/sessions/session.ts:365-375` 调用
`remote.commands.execute(...)`，所以把 `/plan ...` 当普通 MCP 消息发送，计划模式不会被激活。

当前正式 profile 的运行时包已核对为 `0.1.5-rc.2`：
`dsh-plan-mode`、`dsh-agent-presets`、`dsh-commands` 均已安装；其中 `dsh-plan-mode` 类型仍暴露
`set(agent, active)`，`dsh-commands` 类型暴露 `execute(agent, line, attachments, signal)`，
`dsh-agent-presets` 类型暴露 `serviceFor(agent, name)`。

#### 对上次联通性测试的修正

上次测试从灵榜的普通消息路径发送任务，Agent 随后调用 `exit_plan_mode` 并得到：

```text
Error: exit_plan_mode is only available in plan mode
```

这个错误符合 DSH 语义：消息路径没有执行 `/plan`，因此模式仍是 inactive。`web` profile 的
`dump-config` 显示宿主层 `plan-mode: disabled: true` 也不是根因。alpha.2 的 Web patch 会有意关闭
宿主层同名 entry，再由每个 Agent preset 的隔离 realm 挂载 `planning -> @deepseek-ai/dsh-plan-mode`
（`packages/preset/agent-presets/presets/standard/agent.cordis.yml:101-125`；正式 rc.2 安装包内容相同）。
此前测试能看到 `exit_plan_mode`，正是 preset 里的计划插件已加载的证据。因此问题不是灵榜 MCP
传输、Session 恢复或权限缺失，而是调用了错误的入口。

#### 推荐实现路径

灵榜控制插件应在拿到目标 Agent 后复用 DSH 原生命令，不直接写 `session.append('plan/mode')`：

1. `ctx.sessionController.resolveAgent(SessionId)` 解析并恢复目标 Agent；
2. 调用 `ctx.commands.execute(agent, \`/plan ${task}\`, [], signal)`；
3. 校验返回值：`undefined` 表示目标 preset 没有挂载 `/plan`，应返回明确的 capability-unavailable；
   成功结果表示模式选择与任务 steer 已按 DSH 语义入队。

这条路径与官方 Web 和 `apps/web/tests/plan-review.e2e.ts:37-44` 相同，会保留
`command/run`/`command/done` 日志、`plan/mode` 状态折叠、turn boundary 和任务消息顺序。
`ctx.agentPresets.serviceFor(agent, 'planMode')` 可以从 host 侧定位隔离服务，但其公开文档标注为
“read addressing”；它适合能力探测和状态读取，不作为灵榜写状态的首选入口。直接调用
`agent.ctx.planMode` 也不行，因为 `planMode` 在 preset 的 `isolate` realm 中，Agent scope 看不到
entry-local 服务。

#### 审批闭环边界

`exit_plan_mode` 激活后会通过 `ctx.userQuestions.ask(...)` 阻塞，Web UI 能显示 `plan-review` 卡并
回答。当前灵榜控制面还没有计划审批 API：`dsh_get_task` 只投影状态、可见助手文本和摘要，
`events.ts` 明确丢弃 `tool-call`/`tool-result` 参数，因此 MCP 调用方看不到待审计划正文；现有
`CONTROL_OPERATIONS` 也没有计划评审/回答权限。运行时调用 `dsh_control_info`（协议 1.0、插件
0.1.0）复核到的授权操作只有 workspace/session/task 三组能力，没有 plan command 或 plan review。

因此分两档：

- **最小可行**：增加一个内部/受控的计划派发路径，复用 `/plan <任务>`；计划在 Web 的原生评审卡
  上批准或退回。只需引入 `dsh-commands` peer 类型并补命令通道测试。
- **MCP 全闭环**：在此基础上新增按 task/session 绑定的待审计划查询与回答能力，至少包括
  `approve`、带反馈的 `keep planning`、取消/超时、调用方 ACL 和并发归属；回答必须进入
  `userQuestions` 的 answerer seam，不能用普通 `session.prompt()` 冒充。该部分是独立的中等改动，
  不是 profile 开关或插件权限修复。

结论：DSH 原生计划模式在当前 rc.2 宿主和 alpha.2 参考实现中均可用；没有
`create_plan`/`enter_plan_mode` 工具名。灵榜已具备把任务交给 Agent 的能力，但要进入原生计划模式
必须新增命令桥（优先 `/plan <任务>`）；是否把审批也交给 MCP，需要另行实现 userQuestions 桥接。
